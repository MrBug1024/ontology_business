# 能力平台架构、迁移与接入指南

本文说明本平台升级后的稳定边界、运行模型、Provider 开发约束以及 REST、MCP、SDK 接入方式。本文面向平台研发、业务能力 Provider 开发者、企业集成团队和第三方 Agent 开发者。

本平台的职责是把业务语义和业务处理方法建设为可发现、可版本化、可治理、可审计的能力，并把这些能力交给任意 Agent 或客户端使用。平台内的 Agent 是验证客户端，不是客户最终业务终端；目录中的样本数据是建模证据、测试夹具或可治理资源，不是某个场景永久不变的最终业务数据。

## 1. 稳定架构边界

### 1.1 三层模型

```text
Definition plane
  Ontology + Function/Action/Workflow + CapabilityPort + Schema + policy
  形成不可变 Definition hash

Deployment plane
  Definition + explicit release + scenario defaults + connector binding
  形成 deployment fingerprint

Invocation plane
  Actor + typed inputs + managed reference overrides + confirmation/idempotency
  Head 立即固定为 Version，形成 data-context fingerprint 和 Receipt
```

- 新版 capability contract 描述能力是什么、需要什么，不保存客户某一批数据的 ID、数据库凭据、物理表名或临时附件。兼容期内旧 `RuntimeDefinition` 的 mapping 仍可能携带 `data_source_id/table_name/column_map`；这些字段属于内部执行兼容边界，不进入公共 REST/MCP manifest 或 Receipt 的平台控制元数据，Provider 对外输出也必须将它们投影为语义字段、受管引用或哈希。
- `Deployment` 解析明确的 Definition/Release、租户、逻辑 binding key、受管版本和连接器；部署配置不决定数据与权限。
- `Invocation` 提交当前业务请求。文本、结构化参数和本次受管数据引用都属于调用输入，更换数据不要求重新建模或重新发布。

三个身份必须分开使用：

| 身份 | 变化原因 | 用途 |
| --- | --- | --- |
| `definition_hash` | 本体、能力契约、端口、Provider 版本或配置变化 | 判断业务能力版本是否变化 |
| `deployment_fingerprint` | Release、受管绑定或连接器身份变化 | 判断部署解析是否变化 |
| `data_context_fingerprint` | 本次最终固定的数据版本或连接器签名变化 | 判断本次调用实际用了什么数据 |

因此，同一个 Definition 先后处理数据版本 A 和 B 时，`definition_hash` 必须相同，`data_context_fingerprint` 必须不同。

### 1.2 数据用途平面与可选数据

`DataAsset` 与 `LogicalDataset` 都带有服务端和数据库共同约束的 `usage_plane`：

| `usage_plane` | 含义 | 允许的直接用途 |
| --- | --- | --- |
| `modeling_material` | 用于理解结构、生成候选和建立建模 Schema 的资料 | 建模证据、语义映射和能力内容契约来源 |
| `invocation_input` | 验证中心或某次调用准备的正式输入 | Agent/REST/MCP/SDK 的受管运行输入 |
| `generated_output` | 产物或无法由存量证据确定用途的保守默认值 | 输出；作为后续能力输入时必须逐次显式绑定 |

创建目录资产或数据集时必须显式提交该字段；内部/存量无法证明用途的对象按 `generated_output` fail closed。`GET /api/catalog/assets` 和 `GET /api/catalog/datasets` 支持用 `usage_plane` 精确过滤，但列表过滤不是权限或用途裁决的替代品。`purpose=managed_asset` 的受管上传形成 `modeling_material`，`validation_asset` 与 `invocation_attachment` 形成 `invocation_input`，既有对象不能通过改名、标签或换入口原地跨平面。

目录侧的建模元数据只能来自 `modeling_material`：`modeling_evidence` 场景绑定、语义映射以及引用 Dataset Schema 的能力端口都会重新检查数据集平面。通用受管输入解析和选项目录、Agent Turn 附件选择都拒绝 `modeling_material`；`generated_output` 仍可作为能力链的下一步显式受管输入。验证数据包构建只接受 `invocation_input`，上传任务的就绪结果也必须处于该平面。验证中心生成的资产、解析结果、数据包和历史调用都不能反向贡献语义映射、端口契约或下拉选项。旧 `DataSource.resource_scope="modeling"` 仍是连接器/文件桶的兼容建模边界，不等于允许绕过 Catalog 的 `usage_plane`。

能力端口在用途平面之外继续按角色表达数据需求：

- `modeling_evidence`：帮助理解字段、结构、关系和业务含义，不进入生产运行绑定。
- `test_fixture`：用于确定性验证和回归，不自动成为客户运行数据。
- `invocation_input`：每次调用提供的当前数据或文档。
- `reference`：可复用参考知识，可显式固定或跟随受管版本。
- `rules`：规则表、阈值或政策版本，发布门禁必须验证其绑定。
- `output`：能力产物，不作为输入反向固化。

没有数据端口的能力是完整、合法的能力。它可以只接收文本或结构化参数；readiness 不得因为缺少 `DataSource`、`Dataset` 或 `Mapping` 而失败。

### 1.3 运行输入解析

运行输入只接受受管引用：`DatasetVersion`、`DatasetHead`、`AssetVersion` 或受信 `ConnectorBinding`。解析器按以下优先级确定每个端口：

1. 本次调用的 managed input override。
2. 当前环境的场景默认绑定。
3. 端口允许连接器且不存在数据集默认绑定时，解析当前环境的受信 `ConnectorBinding`。
4. 缺少非必填端口时保持为空；缺少必填端口时返回结构化 readiness/validation 错误。

`release_pinned` 不是第三个回退来源，而是一项约束：它禁止调用覆盖，并要求场景默认绑定为 pinned `DatasetVersion`；发布门禁会验证该版本已就绪。

`DatasetHead` 只用于选择，调用开始时立即固定为不可变 `DatasetVersion`。调用过程中不会跟随 Head 漂移。目录 Head 更新支持 `expected_dataset_version_id` compare-and-set，陈旧写入会被拒绝。

`managed_inputs` 只接受固定的受管 selector，不能提交连接串、密码、SQL、物理表名、MinIO 路径或 import path。Provider Definition 的 `runtime_config` 顶层也只接受 `provider_key/provider_version/provider_config`；平台递归拒绝 `provider_config` 中的敏感键名，以及明显包含 SQL、连接 URI、凭据赋值、连接参数或绝对物理路径的字符串。该扫描是通用安全门禁，不会猜测所有领域纯值的业务含义，因此 Provider 仍必须对完整 `provider_config` 和普通 typed `inputs` 使用封闭 Schema，明确排除未声明字段、凭据、物理查询字段和连接配置。连接器只通过服务器已登记的 `binding_key` 解析；Receipt 的平台身份字段只返回安全身份和哈希，Provider 输出的数据边界见 5.6 节。

Agent 规划 prompt 不包含 typed input 的原始值，只包含有界、无值的字段形状和内容哈希；完整 typed input 在选定能力后由统一调用内核直接交给 Provider，并继续受该能力的封闭输入 Schema 和总大小限制约束。大批量记录不能借 `inputs` 进入模型上下文，必须使用受管附件、DatasetVersion 或受信 ConnectorBinding，再由工具按契约做有界查询或检索。

数据连接器的显式健康检查会读取有界的关系名、字段名、逻辑类型和可用行数，并在 `ConnectorBinding` 保存无凭据 `structure_profile` 及其 SHA-256 `structure_fingerprint`。连接目标、物理 endpoint、连接参数、凭据和业务行都不进入该轮廓。声明内容契约的 connector 端口只对这份最近受检轮廓做确定性匹配；连接目标变更或检查失败会清空轮廓并要求重新检查，不能由客户端或 LLM 提交结构描述替代。

### 1.4 可选的输入内容契约

端口的普通 `schema_document` 可以不声明内容契约；此时受管输入仍按 `binding_kinds`、`required` 和 `cardinality` 校验。需要按表格内容自动匹配时，端口在 Schema 中使用可选扩展 `x-platform-input-contract`，当前版本为 `tabular-content/v1`。端口若引用一个 `modeling_material` Dataset Schema 且尚未显式声明该扩展，服务端会从获授权的关系/字段元数据生成有界契约。

建模资料文件桶上传的内容若被服务端识别为表格，会在同一事务中自动生成 `modeling_material` 的 schema-only 契约来源；它只有逻辑 Dataset 与 Dataset Schema，不创建 DatasetVersion，因此不会成为正式运行数据。非表格文件仍只进入资料检索流程。删除对应文件或整个建模资料源会退役未发布页面中的契约来源；同一资料源重传相同内容时按受管来源身份与内容哈希幂等恢复，已发布 Release 快照不受影响。

匹配依据是解析后的结构轮廓，包括字段名及别名、逻辑类型、必填字段和最低数据行数；文件名、工作表/关系显示名、对象存储位置和原始业务行不参与匹配。服务端生成的契约允许额外字段与额外关系，因此业务文件可以比最低契约更丰富。一个输入同时匹配多个端口、或多个输入命中 `cardinality=one` 端口时会以歧义错误失败；`cardinality=many` 会保留该端口的全部不同受管输入并逐条形成审计绑定。未命中任何端口的额外文件保留为本轮补充附件，不会因为存在额外文件而让已满足的能力契约失败。协议层允许同一 `port_key` 提交多个不同 selector，但拒绝完全重复的 selector，最终基数仍由服务端端口契约裁决。

该扩展是封闭契约：契约、关系和字段层出现未声明键都会失败；字段别名、名称长度和关系数量都有界；同一字段不能同时声明冲突的单类型与多类型。哈希前先按协议规则规范化，拒绝 `NaN`、Infinity 和不能确定编码的对象，客户端或 LLM 不能靠附加任意字段改变匹配语义。

### 1.5 Schema-first 语义映射

新建语义映射直接绑定获授权的 `modeling_material` Dataset Schema，不要求也不创建运行数据绑定。映射定义保存语义属性到逻辑字段的可移植关系；普通映射中的 transform、identifier/filter/condition 等未版本化执行片段必须为空，专用解释进入精确版本的受信 Provider。发布快照递归封闭并规范化映射文档，运行时只消费该冻结快照，不回读可变 authoring 行。

查询时，`DatasetHead` 只用于选择并立即固定为其当时的 `DatasetVersion`；属性 ACL 对请求属性、查询模板和最终 `column_map` 采用 deny-first 校验，未授权属性不能借模板或物理列映射进入结果。验证中心的数据集和映射不会成为建模语义来源。

## 2. 统一执行链路

REST、MCP、SDK 和验证 Agent 使用同一个应用服务和 `CapabilityInvoker`：

```text
protocol adapter
  -> authenticate Actor and scopes
  -> resolve immutable Definition and Deployment
  -> resolve and pin RuntimeDataContext
  -> validate schema, readiness, ACL and idempotency
  -> resolve trusted CapabilityProvider
  -> execute / preview / confirm
  -> persist CapabilityInvocation + RunInputBinding
  -> return protocol-neutral Receipt
```

协议适配器只负责认证和协议转换，不实现业务分支。统一内核负责：

- 租户、角色、scope 和场景 ACL；
- 输入 JSON Schema、受管引用和期望 hash 校验；
- 无副作用调用、预演、确认、幂等和中断恢复；
- 调用主体、来源、数据版本和证据审计；
- 输出脱敏、错误稳定化和 Receipt 查询。

副作用能力必须先 `preview`，再把服务器签发的确认票据原样用于 `confirm`，并提供幂等键。Provider 向下游传播的是平台派生的执行键，不能直接传播调用者原始幂等键。

### 2.1 持久 Agent Turn

登录态验证 Agent 使用持久 Turn API；创建请求必须带 `idempotency_key`，服务端在同一事务中保存用户消息、占位回复、加密请求载荷、Turn 和首个事件后立即返回 `202 Accepted`：

```text
POST /api/agents/{agent_id}/turns
GET  /api/agents/{agent_id}/turns?conversation_id=...&active_only=true
GET  /api/agent-turns/{run_id}
GET  /api/agent-turns/{run_id}/event-log?after_revision=...
GET  /api/agent-turns/{run_id}/events
POST /api/agent-turns/{run_id}/cancel
POST /api/agent-turns/{run_id}/retry
```

SSE 端点以持久事件 revision 作为 event id，客户端重连时使用 `Last-Event-ID` 续读；断开页面订阅只停止传输，不等于取消后台 Turn。取消请求必须提交 `expected_revision`，状态漂移返回冲突。只有 `failed`、`cancelled` 或 `indeterminate` Turn 可重试；重试还要提交新的幂等键，并创建带 `parent_run_id` 的新 Turn，而不是覆写旧审计事实。外部工具可能已经开始后再取消或遇到未知异常时，结果进入 `indeterminate`，调用方必须先核对，不能盲目重放。

旧 `POST /api/agents/{agent_id}/chat` 在兼容期继续返回 `200 text/event-stream`，但它只是上述持久 Turn 的弃用观察门面：先原子受理，再通过短会话读取持久事件和最终 Message，翻译为旧 SSE envelope。它不会在 HTTP 请求内 claim、准备数据或调用 LLM，浏览器断流也不会取消 Turn；响应通过 `Deprecation`、`Link`、`Location` 和 `X-Agent-Turn-Id` 指向新的 `202` API。旧调用方未提供幂等键时，服务端为该次请求生成唯一兼容键；新调用方必须显式提供稳定幂等键。

Turn 的创建、读取、事件、取消与重试都以服务端认证主体为权威，并同时限定 `tenant_id`、发起用户、Agent/场景权限和会话归属；客户端不能提交或切换租户。worker 从持久行恢复原始 tenant/user principal，并重新校验发起人、Agent 与场景，失效后不会匿名执行或提升权限。进入模型的历史最多取最近 24 条来源消息，并受 48,000 字符的总序列化上限约束；工具调用与结果按一组保留，不会用无限历史挤占当前请求的数据边界。

### 2.2 LLM 大数据边界

上传文档全文只作为服务端解析和索引来源，表格原始行只由受限数据工具读取。进入 LLM prompt 的只有附件清单、内容 hash 等安全元数据，以及按当前问题检索出的可引用片段；对象存储坐标不会跨越该边界。普通对话默认最多取 5 个片段、合计 4,000 字符，建模编译默认最多 20 个片段、合计 16,000 字符；通用硬上限是 20 个片段和 24,000 字符。助手 JSON 请求体限制为 128KiB，`selection` 使用封闭字段并限制为 8KiB；操作参数只用于服务端确定性预演，不进入 LLM prompt。`retrieval_complete=false` 表示模型没有读完原文，不能声称已经完整覆盖附件。`search_documents` 和兼容的 `read_document` 都只返回有界片段，后者不再是全文读取旁路。

### 2.3 持久全局助手请求

带附件的全局助手请求先在单个事务中保存用户消息、助手占位消息和 `AssistantRequestRun` intent，然后立即返回；后台等待对应 `ManagedUploadRun` 就绪后再执行。读取、取消、重试、幂等重放以及 worker 最终写入都会重新验证 tenant、发起用户、线程归属和当前场景 ACL。耗时外部调用结束后，worker 使用新的数据库会话刷新当前 principal，再以 lease token/generation 和行锁做最终 fencing；权限已撤销或租约已失效时，迟到结果不能写回。

临时附件资产的 `expires_at` 与调用方获准的上传 TTL 保持一致，解析和执行前都通过统一资产生命周期服务确认版本仍可用于新调用。失败请求的人工重试不会改写旧终态：服务端创建带 `parent_run_id` 的子请求，并为需要重新解析且仍有受管正文的失败上传创建对应子上传；每个父任务最多登记一个直接重试，幂等重放返回同一子任务。附件正文已经过期、取消或从未成功到达服务端时明确要求重新选择文件。

## 3. 能力定义与发布

一个可发布能力至少包含：

1. 稳定的能力 key、名称和说明；
2. 输入、输出 JSON Schema；
3. 所需数据端口及其角色、媒介、必填性、基数和 binding policy；
4. 权限、副作用、确认和幂等策略；
5. 内置执行器类型，或显式的受信 Provider key、版本和纯值配置；
6. 校验证据和候选治理状态。

AI 和人工创建的候选进入同一质量状态机。来源不决定是否可发布；确定性校验、冲突、依赖闭包和风险策略决定晋级资格。Action 晋级为正式定义不等于自动激活。

候选治理使用同一组控制面 API，业务专家验证质量证据，而不是因为来源为 AI 就永久把模型视为不可发布草稿：

```text
GET   /api/scenarios/{scenario_id}/model-drafts
POST  /api/scenarios/{scenario_id}/model-drafts
PATCH /api/scenarios/{scenario_id}/model-drafts/{draft_id}
POST  /api/scenarios/{scenario_id}/model-drafts/{draft_id}/revalidate
POST  /api/scenarios/{scenario_id}/model-drafts/{draft_id}/promote
POST  /api/scenarios/{scenario_id}/model-drafts/promote-batch
```

人工候选、顾问候选和导入候选都先处于禁用的工作副本。编辑、重新校验和晋级请求必须携带当前 `expected_revision`；陈旧请求返回冲突，不会覆盖他人的新版本。重新校验由服务器生成 `validation_status`、`promotion_eligible`、`promotion_blockers` 和 `quality_fingerprint`。单条晋级复用批量晋级路径；批量操作要么全部形成正式定义，要么一个都不落库。任何 blocker、依赖不闭合、revision 漂移或正式化预检失败都会阻止整个批次。Action 即使晋级成功仍保持 `inactive`，必须经过独立激活治理。

兼容助手仍可展示旧的单域本体、映射或工作流建议，但这些 proposal 固定为 `read_only`，页面不提供应用动作，服务端应用端点也返回冲突并指向“完整场景建模”入口；它们不能绕过上述候选状态机直接写 ORM。全局助手创建的场景根对象只会进入 `draft` 生命周期。旧建议若引用建模资料，还必须携带服务器封存的消息、proposal 和精确 RAG 来源 fingerprint；确认时重新校验当前场景 ACL、`resource_scope=modeling`、文件/分块内容 hash 和索引版本。验证中心或本次调用附件不会进入这份来源证明。

建模与显式验证解析当前受治理定义；对外调用使用人工创建并启用的不可变场景 Release。部署环境只选择独立基础设施，不进入业务数据、权限、缓存或队列。发布后修改 ORM 行、嵌套 JSON、端口或绑定不会改变已经解析的当前 deployment；只有重新解析或发布新版本才读取新状态。

### 3.1 消息渠道交付与人工发布

“发布与接入”由人工选择场景、创建正式发布，并显式启用、停用、退役或删除。创建默认停用；删除仅隐藏已退役发布，历史快照及审计继续保留。服务端检查权限、契约与依赖合法性，质量评分不能代替人的发布决定。

业务渠道消费统一 Receipt 的 `delivery.text`、待办和附件。普通分析直接执行；涉及副作用的能力先返回预演，由发起人在原渠道回复确认；审批按配置的人员、角色与佐证要求验证真实操作者。回复携带消息幂等标识和待办 revision，不能将昵称或模型输出当作人员授权。异步任务的真实完成、拒绝、失败或结果未知都通过原调用回执交付，不要求业务人员跳转平台。人工重试不会覆盖原调用的终态。

接入方按 `delivery.revision` 轮询去重并把结果投递回原会话；文件经带身份的下载端点转发。具体 REST、MCP、SDK 消息与文件契约见 [SDK 接入说明](../backend/sdk/README.md#plain-message-delivery)。真实聊天软件的身份映射和消息投递由渠道连接器负责。

## 4. Provider 开发规范

### 4.1 适用范围

Provider 端口是 `CapabilityInvoker` 的内部执行抽象，但这不等于每个业务场景都必须开发自定义 Provider。平台内置的 Function、Action、Rule 和 Workflow 适配器也通过同一端口统一执行；用户定义的封闭动态 Rule 可以直接成为正式、可发现、可审计的能力。只有当能力需要通用适配器尚不支持的专用算法、跨记录/跨对象聚合、特殊数据物化或领域证据解释时，才需要独立的受信业务 Provider。是否需要自定义 Provider 必须由正式 Definition、运行输入契约和实际缺口决定，不能由 AI 生成草稿、空能力目录或某个测试场景名称推断。

以下逻辑应进入独立 Provider，而不能进入 Agent、REST、MCP 或调用内核：

- 行业字段、专用算法和业务规则；
- 场景专用工具、确定性统计、证据解释与 grounding；
- 历史工具名或 namespace 兼容；
- 对特定数据逻辑模型的解释。

当前仓库静态安装了语义数据集查询与语义规则判定 Provider；Function、Action、Rule 和 Workflow 的其余通用能力仍由内置适配器执行。只有正式 Definition 与实际运行验证证明通用能力不足时，才在 `backend/app/providers/<provider_name>/` 增加受信包，并由组合根显式注册精确 `(provider_key, provider_version)` 对象后封闭注册表。数据库只能保存受信 key 和版本，不能注册代码、指定模块路径或动态导入实现。新增或卸载 Provider identity 必须通过受信代码部署完成。

### 4.2 标准接口

Provider 实现协议无关的 `CapabilityProvider`：

```python
class ExampleProvider:
    provider_key = "trusted.example"
    provider_version = "1.0.0"

    def contract(self, capability, deployment):
        return {
            "input_schema": {
                "type": "object",
                "properties": {},
                "additionalProperties": False,
            },
            "required_roles": [],
            "required_scopes": [],
            "side_effect": False,
            "requires_confirmation": False,
            "idempotency_required": False,
        }

    def invoke(self, request, actor, deployment, data_context):
        # 只使用已验证 Actor、冻结 Definition 和不可变 RuntimeDataContext。
        return {...}
```

可选的 `preview()` 和 `recover()` 分别用于副作用预演和中断调用的无副作用对账。若 Provider 需要请求局部依赖，可实现 `bind_invocation(invocation_context)` 并返回新的绑定对象；禁止修改注册表单例。绑定对象的 `provider_key/provider_version` 必须与注册身份精确一致。

Agent 不再使用 `bind_agent_runtime()`、Provider 自定义工具名、legacy/capability shadow 比较或另一套 Provider 执行协议。它只暴露 `list_available_capabilities` 和 `invoke_capability`，后者进入与 REST、MCP、SDK 相同的 `CapabilityInvoker`。Provider 的行业字段、算法和证据解释封装在 `contract()`、`invoke()` 及可选的 `preview()` / `recover()` 内；通用 Agent 主循环不识别业务 namespace、字段或工具名。历史 runtime mode 和 shadow 证据仅作只读迁移审计事实，不能重新启用旧执行路径。

### 4.3 Definition 绑定

Provider 能力使用 `runtime_kind="provider"`，配置必须且只能包含以下三项：

```json
{
  "runtime_kind": "provider",
  "runtime_config": {
    "provider_key": "trusted.example",
    "provider_version": "1.0.0",
    "provider_config": {
      "logical_contract": "example/v1"
    }
  }
}
```

`provider_key`、`provider_version` 和 `provider_config` 都进入 Definition 身份。`provider_config` 只能保存可发布的纯值语义配置；平台会扫描敏感键名和明显危险的字符串值，Provider 仍必须按自己的封闭配置契约校验全部语义与未声明字段。扫描通过不代表某个值已经获得业务授权。

注册表以 `(provider_key, provider_version)` 作为完整的 `ProviderIdentity`，同一个 key 可以显式安装多个版本。Definition 只解析与其声明完全相同的 identity；这里不是 semver 范围匹配，也不会在缺少目标版本时回退到同 key 的最新版。精确版本未安装或绑定对象版本不一致时，能力发现或调用会以安全错误失败，而不会让新实现静默解释旧 Definition。升级时应先并行安装新版本、发布引用它的新 Definition/Release，确认旧 Release 退役后再卸载旧版本。

场景编辑器通过 `GET /api/scenarios/{scenario_id}/function-providers` 获取当前主体可用于函数定义的受信 manifest。manifest 是最大 64 KiB 的纯 JSON 编写元数据，包含精确 identity、封闭 `config_schema`、默认配置、输入/输出 Schema、允许的 UI 控件、弃用状态和迁移说明；它不包含 Python 路径或可执行代码。目前该目录只支持 `function` Provider。前端只能按 manifest 渲染通用表单，保存和 Release 归一化时服务端仍会重新解析同一精确 Provider，并调用 Provider 自有 `validate_definition()`；客户端缓存或修改 manifest 不能授权未注册版本或非法配置。

### 4.4 Provider 验收清单

- Provider 单元测试覆盖 contract、输入 Schema、版本拒绝、ACL 和安全错误。
- 有数据能力至少验证两个受管版本 A/B，结果和 provenance 只引用本次版本。
- 零数据能力验证不创建 DataSource、Dataset、Mapping 仍可调用。
- Agent、REST、MCP 的输出语义及 Definition/Deployment/DataContext provenance 一致。
- 兼容 alias 只存在于 Provider 自有 manifest。
- 架构扫描确认平台内核无行业名、字段名和固定工具名。

### 4.5 内置执行器的数据上下文边界

普通 JSON 参数与受管数据端口是两类不同输入。当前执行器支持矩阵如下：

| 执行器 | `inputs` 类型化参数 | 非空 `RuntimeDataContext` |
| --- | --- | --- |
| builtin Function | 支持 | 当前拒绝 |
| builtin Action | 支持，保留预演/确认/幂等 | 当前拒绝 |
| builtin Workflow | 支持，异步载荷加密恢复 | 当前拒绝 |
| trusted Provider | 按 Provider contract | 必须显式消费、校验并形成 provenance |

因此，声明了受管数据端口的能力必须使用实现相应 typed materializer 的受信 Provider。平台不会因为端口存在，就让内置执行器静默忽略数据上下文并返回看似成功的结果；尚未支持时统一 fail closed。

## 5. REST v2 接入

### 5.1 创建凭据

管理员通过 `POST /api/developer/api-keys` 创建带以下 scope 的 API key：

```json
{
  "name": "enterprise-agent",
  "scopes": ["capabilities:read", "capabilities:invoke", "assets:write"]
}
```

原始 `ont_sk_...` token 只在创建响应中返回一次。生产环境通过 HTTPS 传入 `X-API-Key`，不得放入 URL、日志或前端持久存储。

凭据管理端点为 `GET /api/developer/api-keys`、`POST /api/developer/api-keys` 和 `DELETE /api/developer/api-keys/{key_id}`。列表与吊销响应只包含元数据，不会再次返回原始 token。只做零数据或引用既有目录版本的客户端不需要 `assets:write`；只有需要提交新文件的集成才授予该独立 scope。

### 5.2 发现场景、能力与受管输入选项

第三方 Agent 不需要从平台 UI 或人工配置中取得 `scenario_id`。先用同一把 API key 获取当前主体有权读取的活动场景：

```http
GET /api/external/v2/scenarios
X-API-Key: ont_sk_...
```

响应只包含逻辑场景的 `id/name/description/industry`，按 API key 所属租户和场景 read ACL 过滤，并排除已退役场景；不会返回租户内部配置、数据源或物理存储信息。选定场景后发现能力：

```http
GET /api/external/v2/scenarios/{scenario_id}/capabilities?release_id={release_id}
X-API-Key: ont_sk_...
```

当前 REST v2 可发现和调用的 `kind` 为 `function`、`action`、`rule`、`workflow`。响应给出 `kind`、`key`、输入/输出 Schema、数据端口、`readiness.ready/issues`、`definition_hash` 和 `deployment_fingerprint`。Rule 接受封闭的 `record` typed input，并始终只返回判定与待确认的 Action 意图，不直接执行副作用。公开 issue 的 `axis` 为 `definition`、`validation` 或 `runtime`；客户端应在调用时回传两个期望 hash，以防发现和执行之间发生部署变化。

每个能力响应中的 `data_ports` 只包含明确归属当前 `{kind, key}` 的端口。客户端不得读取或猜测同场景其他能力的端口：文本、数字、普通对象和数组始终按 `input_schema` 放入 `inputs`，不能为了提交参数而先创建资产。只有 `direction=input` 且 `allow_override=true` 的端口才能出现在 `managed_inputs`，selector 类型还必须属于该端口返回的 `binding_kinds`；`release_pinned` 或 `allow_override=false` 的端口不得按次覆盖。

对允许逐次覆盖的端口，客户端通过当前能力和端口限定的目录获取可用逻辑引用，而不是调用控制面数据源 API 或猜测内部 ID：

```http
GET /api/external/v2/scenarios/{scenario_id}/capabilities/{kind}/{capability_key}/ports/{port_key}/managed-input-options?release_id={release_id}&limit=100&offset=0
X-API-Key: ont_sk_...
```

选项目录再次验证场景 ACL、冻结 Definition、当前 Deployment、端口归属、`allow_override` 和 `binding_kinds`。响应带分页信息、`definition_hash`、`deployment_fingerprint`、端口允许的 selector 类型，以及可以直接放入调用请求的 `items[].managed_input`（含服务器校验过的 selector 与 `expected_signature`）。客户端应原样提交该对象并回传两个身份 hash。响应不会暴露 DataSource ID、对象路径、物理表列、连接目标、连接配置或凭据。

### 5.3 零数据能力调用

```http
POST /api/external/v2/scenarios/{scenario_id}/capabilities/function/{capability_key}/invoke
X-API-Key: ont_sk_...
Content-Type: application/json

{
  "release_id": "release-id",
  "mode": "execute",
  "inputs": {
    "request": "整理这些零散需求并输出验收标准",
    "fragments": ["需要权限隔离", "支持批量导入"]
  },
  "managed_inputs": [],
  "expected_definition_hash": "<discovery response>",
  "expected_deployment_fingerprint": "<discovery response>"
}
```

零数据能力不需要构造空 DataSource 或伪造 Mapping。

### 5.4 每次提供不同数据

```json
{
  "release_id": "release-id",
  "mode": "execute",
  "inputs": {"threshold": 0.8},
  "managed_inputs": [
    {
      "port_key": "records",
      "dataset_version_id": "<governed-version-b>",
      "expected_signature": "<optional-current-signature>"
    }
  ],
  "expected_definition_hash": "<discovery response>",
  "expected_deployment_fingerprint": "<discovery response>"
}
```

支持的 selector 为 `dataset_version_id`、`dataset_head_id`、`asset_version_id`、`artifact_id` 或 `binding_key`；每个 `managed_inputs` 条目必须且只能带一个 selector。同一 `port_key` 可以提交多个不同条目，`cardinality=many` 会解析并逐条审计全部输入；`cardinality=one` 收到多个匹配输入时拒绝歧义。完全重复的 selector 在协议边界直接失败。当前 `artifact_id` 是 `DataAssetVersion.id` 的兼容别名，不是第二套 Artifact 权威。使用 Head 时，精确的最终 Version 保存在内部 `RunInputBinding` 和调用审计中，Receipt 顶层使用 `data_context_fingerprint` 表达统一的数据上下文身份。若能力的输出契约需要可核验 provenance，Provider 可以返回当前主体已获授权的受管 `reference_id/version_id/signature`；这些是目录逻辑引用，不是物理 DataSource、对象存储位置或连接配置。

### 5.5 文档和调用附件

二进制内容不能直接塞入 invocation JSON。第一方登录态验证 Agent 使用持久上传任务：

```text
POST /api/catalog/upload-runs
POST /api/catalog/upload-runs/content
GET  /api/catalog/upload-runs/{run_id}
POST /api/catalog/upload-runs/{run_id}/retry
```

第一步用 JSON 登记 `filename`、声明字节数、媒体类型、`validation_asset` 或 `invocation_attachment` 用途和幂等键，立即以 `202 Accepted` 返回 `awaiting_upload` 状态与 revision；幂等范围由服务端限定为当前 tenant 和用户，同一键不能登记不同请求。第二步向固定的 `/content` multipart 端点提交 `upload_run_id`、`expected_revision` 和文件。服务端在消费文件前校验登录主体、租户和任务所有者，分块暂存后、写入 MinIO 前再加锁校验 revision 并取得上传 lease；实际字节数必须与声明一致，内容 SHA-256 和对象完整性会被复核。客户端不能提交桶、object key 或凭据。

每次 MinIO PUT 前还会先独立提交一个持久对象上传 intent，并以 generation/token heartbeat 保护上传窗口；只有 intent、上传任务 lease 和对象身份都仍匹配，目录元数据才可在事务中变为可见。进程在 PUT 后、目录提交前崩溃时，清理 worker 能从该 intent 识别并回收孤立对象，避免 PostgreSQL/MinIO 双写留下不可审计文件。

内容持久化后请求返回 `202 Accepted`，任务由后台 worker 按 `stored -> processing -> ready/failed` 推进；客户端轮询 GET，只有 `ready` 才会得到可用于后续调用的资产版本。上传与解析分别使用 lease generation/token 和最终写入 fencing；进程中断后，过期的 `uploading` lease 回到 `awaiting_upload`，过期的 `processing` lease 可被其他 worker 接管。失败任务按当前 `expected_revision` 重试；旧终态保持不可变，服务端为仍可恢复的受管正文创建带 `parent_run_id` 的子任务，没有已持久化正文或正文已经过期时要求重新选择文件。两种用途都生成 `invocation_input` 资产；`validation_asset` 可保存复用，`invocation_attachment` 带 TTL，不能通过该入口生成建模资料。

Agent Turn 可以在上传仍处于 `awaiting_upload/uploading/stored/processing` 时携带同一用户的 `upload_run_id` 并先获得 Turn 的 `202 Accepted`；Turn 在 `preparing_inputs` 中等待任务就绪，再把它固定为带内容签名的 `asset_version_id`。上传失败、过期、跨租户或跨用户引用都会由服务端拒绝，页面取消上传请求也不会伪造后台任务已经取消。

第三方 Agent 使用独立的 `assets:write` scope 调用：

```http
POST /api/external/v2/assets/upload
X-API-Key: ont_sk_...
Content-Type: multipart/form-data

file=@requirements.docx
name=current-requirements
expires_in_seconds=3600
```

外部 multipart 只接受：

- `file`：CSV、XLSX 或支持解析的文档；
- `name`、`description`：可选逻辑元数据；
- `expires_in_seconds`：可选；临时附件默认 24 小时，可在允许范围内显式缩短或延长。

平台按当前 API key 的租户在服务端解析受管上传桶，并强制 `purpose=invocation_attachment`。请求不能提交 `file_bucket_id`、桶名、对象路径、endpoint、前缀、连接参数或凭据；未知字段也会失败。受管上传使用 `CATALOG_MAX_UPLOAD_BYTES`，默认单文件 2 GiB；Office 容器还受默认 8 GiB 展开上限、成员数和压缩比校验约束。API 全程分块写入私有暂存文件并流式上传 MinIO，不按文件大小占用同等内存。反向代理的请求体和超时必须至少覆盖该边界及 multipart 开销；旧 `MAX_UPLOAD_BYTES=50 MiB` 只约束仍以内存接收请求的兼容 API。临时调用附件默认保留 24 小时，调用方可在 300 秒到 7 天之间选择 TTL。

文件经过格式、签名、大小和压缩容器检查后形成内容身份、hash 与审计引用不可变的 `DataAssetVersion`。在有效期内重复上传相同内容会返回同一版本并令 `created=false`；到期后，逻辑版本保留并转为 `retired`，物理 `BucketFile`/MinIO 载荷通过删除 Outbox 分离和清理，历史 `RunInputBinding` 仍能追溯内容 hash，但该版本不能用于新调用。到期后再次上传相同内容会形成新的版本身份。响应只返回 `purpose/temporary/expires_at/created` 以及嵌套的 `{ "asset": {...}, "version": {...} }`，不返回物理存储身份。随后把 `response.version.id` 作为 `asset_version_id` 提交到该能力自己的文档端口。

第一方目录控制面的兼容单请求入口仍是 `POST /api/catalog/uploads`，由已获目录写权限的用户显式选择当前租户受管文件桶。持久上传任务、兼容控制面上传和外部上传共用相同的原子目录写入、内容去重、生命周期和失败清理服务；外部路径永远不能选择物理桶。

验证中心默认使用 `purpose=validation_asset`：文件上传一次后持续出现在当前租户的验证资料库中，可跨对话复用，直到用户显式删除；“仅本次”模式仍使用有 TTL 的 `invocation_attachment`。同一次消息选择的 CSV/XLS/XLSX/TSV 会在后台流式转换成内容寻址的 zstd Parquet 数据集，按约 256 MiB 自动分片，再以一个 `dataset_version_id` 绑定到能力的数据端口。Agent 上下文只接收逻辑引用、Schema 和受限查询结果，不接收几万或几十万原始行。

删除验证资料会退役逻辑资产和版本，并通过删除 Outbox 清理 MinIO 原始对象及由它生成的数据集分片；历史调用仍保留内容 hash 和逻辑审计引用。能力 Definition、Release 和已发布场景不会保存这批验证文件的物理引用，因此删除验证资料不会改变已建模、已验证或已发布的能力。第三方正式调用仍必须按能力端口自行提供本次 `DatasetVersion`、文件版本或远程连接 binding。

### 5.6 Receipt

调用返回 `invocation_id`、状态、三个身份 hash、输出、审计引用和确认信息。可使用：

```http
GET /api/external/v2/invocations/{invocation_id}
X-API-Key: ont_sk_...
```

Receipt 查询要求 `capabilities:read` scope、同租户、当前场景 read ACL，并且 `principal_type/principal_id` 与原调用完全相同。对于外部 REST/MCP 调用，`principal_id` 是 API key ID，而不是它所属的用户 ID；因此同一把 key 可以跨 REST/MCP 查询自己的调用，但轮换后的新 key 不能查询旧 key 创建的 Receipt。

Receipt 中的数据分为两类：

- 平台控制与来源元数据：调用身份、三个 fingerprint、状态、确认信息和审计引用，不包含凭据、物理连接配置或未授权引用。
- `output`：Provider 按能力输出契约产生的授权业务结果，可能包含客户提交内容或派生业务数据，也可能包含已授权的受管逻辑引用；它必须经过输出 Schema、属性 ACL、脱敏和大小限制，不得包含 DataSource ID、物理表列、对象存储坐标、连接配置或凭据。

## 6. MCP 接入

通用 MCP 与 REST v2 使用同一个 `ont_sk_...` 凭据和统一 Invoker：

```json
{
  "mcpServers": {
    "business-capabilities": {
      "type": "http",
      "url": "https://platform.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ont_sk_..."
      }
    }
  }
}
```

提供三个通用工具：

- `list_capabilities`：按 `scenario_id` 和可选 `release_id` 发现契约，返回 `{ "capabilities": [...] }`；
- `invoke_capability`：对 `function/action/rule/workflow` 提交 typed inputs、managed inputs、模式和期望 hash；
- `get_capability_receipt`：查询统一回执。

当前 MCP 工具集不提供场景目录和受管输入选项目录。纯 MCP 客户端需要由部署方提供已授权的 `scenario_id` 和逻辑受管引用；需要自主引导的客户端应先使用同一凭据调用 REST v2 的场景与端口选项端点，或直接使用 Python SDK，再通过 MCP 调用能力。MCP 不会退化为暴露物理数据源目录来填补这一边界。

MCP 网关不承载 multipart 二进制上传。需要提交新文档时，客户端先用同一 `ont_sk_...` 凭据和独立 `assets:write` scope 调用 REST `/api/external/v2/assets/upload`（或 SDK 的 `upload_invocation_attachment`），再把返回的 `version.id` 作为 `asset_version_id` 交给 MCP `invoke_capability`。因此 MCP 是能力调用协议，受管附件上传是配套 REST 数据入口；不具备 HTTP 上传能力的纯 MCP 客户端不能提交新二进制文件。

同一个 `/mcp` 网关还会发布兼容工具 `invoke_agent`，因此工具发现结果不止上述三个名称：`ont_sk_...` 只授权通用 capability 工具，旧 `agt_sk_...` 发布凭据只授权它绑定的 `invoke_agent`。`invoke_agent` 不是新集成的主路径；新客户端不应依赖平台 Agent ID、固定数据源列表或业务专用 MCP 工具名。

## 7. Python SDK

`backend/sdk/ontology_platform_sdk.py` 是本仓库随源码交付的辅助模块，并非已发布到公共包仓库的安装包；从 `backend` 目录运行集成代码，或把仓库的 `backend` 目录加入 `PYTHONPATH`。它把两个协议版本作为独立接入入口：`OntologyPlatformClient` 使用 `/api/external/v1` 做旧的只读场景/对象访问，`CapabilityClient` 使用 `/api/external/v2` 做场景/能力发现、受管选项选择、附件上传、调用和 Receipt 查询。两者不能共用同一个 base URL；`CapabilityClient` 不复制 Provider 逻辑：

```python
from sdk import CapabilityClient

with CapabilityClient(
    "https://platform.example.com/api/external/v2",
    "ont_sk_...",
) as client:
    scenario = client.list_scenarios()[0]
    contract = client.list_capabilities(scenario["id"], release_id="release-id")[0]
    uploaded = client.upload_invocation_attachment(
        "requirements.docx",
        document_bytes,
        content_type="application/vnd.openxmlformats-officedocument.wordprocessingml.document",
        expires_in_seconds=3600,
    )
    receipt = client.invoke_capability(
        scenario["id"],
        contract["kind"],
        contract["key"],
        release_id="release-id",
        inputs={"request": "分析当前输入"},
        managed_inputs=[{
            "port_key": "requirements",
            "asset_version_id": uploaded["version"]["id"],
        }],
        expected_definition_hash=contract["definition_hash"],
        expected_deployment_fingerprint=contract["deployment_fingerprint"],
    )
    same_receipt = client.get_invocation_receipt(receipt["invocation_id"])
```

副作用能力必须显式完成预演和确认，不能把 `execute` 当作旁路：

```python
action_contract = client.get_capability(
    scenario["id"], "action", "capability-key", release_id="release-id"
)
preview = client.invoke_capability(
    scenario["id"], "action", "capability-key",
    release_id="release-id", mode="preview", inputs={"request_id": "R-1001"},
    expected_definition_hash=action_contract["definition_hash"],
    expected_deployment_fingerprint=action_contract["deployment_fingerprint"],
)
confirmed = client.invoke_capability(
    scenario["id"], "action", "capability-key",
    release_id="release-id", mode="confirm", inputs={"request_id": "R-1001"},
    confirmation=preview["confirmation"],
    idempotency_key="enterprise-agent:R-1001",
    expected_definition_hash=action_contract["definition_hash"],
    expected_deployment_fingerprint=action_contract["deployment_fingerprint"],
)
```

`CapabilityClient` 当前支持 `function/action/rule/workflow`。SDK 默认要求 HTTPS、拒绝 URL 凭据且不跟随带凭据重定向。本地回环联调必须显式设置 `allow_insecure_http=True`，并且目标主机必须是 localhost 或数值回环地址。

## 8. 存量迁移与回退

### 8.1 数据库迁移

按 Alembic 增量升级，不删除存量表：

```powershell
cd backend
python -m alembic -x use_admin=1 upgrade head
```

部署和验收必须分别执行 `alembic heads` 与 `alembic current`，从当前迁移目录读取 single head 并核对目标库，不能把文档中的 revision 记录代替仓库事实。迁移 `20260827_02` 引入可恢复的 `PlatformMigrationRun/Checkpoint` 台账；`07` 增加 capability ports、invocations 和 `RunInputBinding`，`08` 增加 Agent 逐次输入审计，`09` 将异步 Workflow 输入迁移为 AES-256-GCM 加密载荷，`10` 把每个数据端口显式归属到一个 Function、Action 或 Workflow，`11` 支持临时附件到期后保留逻辑版本并分离物理载荷，`12` 增加 Release 撤下审计事实，`20260904_18` 增加用途平面和持久 Agent Turn，`20260904_19` 增加持久受管上传任务，`20260904_20` 关闭历史建模来源污染，`20260904_21` 闭合持久 Turn/上传任务归属并保存 Connector 结构轮廓，`20260904_22` 增加带附件全局顾问请求台账及会话/消息复合归属约束，`20260905_23` 把新语义映射改为建模 Schema-first 并冻结可移植契约，`20260905_24` 为助手请求和上传重试增加租户闭合的父子审计链。`10` 只接受端口 `config.contract_source` 及已治理草稿解析关系作为存量归属证据；无法唯一证明的行会让迁移 fail closed，不能按名称、端口前缀或“场景只有一个能力”猜测。执行涉及既有 WorkflowRun 的 `09` 升级前，部署必须提供：

```ini
WORKFLOW_PAYLOAD_ACTIVE_KEY_ID=<active-key-id>
WORKFLOW_PAYLOAD_ENCRYPTION_KEYS={"<active-key-id>":"<urlsafe-base64-32-byte-key>"}
```

密钥只进入部署 Secret Manager，不能写入仓库、数据库或日志。轮换时先把新 key 加入 key ring，再切换 active id；旧 envelope 继续按自身的 `key_id` 解密。当前没有历史载荷 rewrap，也没有以“配置的留存期已过”替代实际删除的机制。只有确认所有引用旧 `key_id` 的现存 `WorkflowRun` 已实际删除，并且允许 downgrade 的回滚窗口也已经结束，才能移除旧 key；任一存量行仍引用它时，运行恢复、重试或 `09` downgrade 都会 fail closed。

`09` downgrade 会在事务内解密全部现存 envelope，把数据库列恢复为旧版明文输入，然后删除加密摘要列。因此它是会降低静态数据保护级别的紧急回退，不是普通无风险回滚；执行前必须确认完整历史 key ring 可用，并按明文载荷重新落实数据库访问、备份和留存保护。

`20260904_20` 在退役当前污染的建模绑定、语义映射、关系映射和能力端口前，只检查不可变 Snapshot 自身：存在非空 `dataset_schema_hash`、非空或畸形 `semantic_mapping_ids` 的历史 catalog-derived 定义，却没有当时可持久化的不可变来源证明时，保守把仍为 `released` 的记录改为 `rolled_back` 并写入固定系统原因。它不 JOIN 当前 port、mapping 或 dataset，因此这些 authoring 行被删除、重绑或修改都不能绕过；零数据和不引用目录 Schema 的 manual/direct 契约不受影响。Snapshot 内容本身不被重写。该迁移不可逆，`downgrade()` 会主动失败，因为原有资格与发布状态不能在不破坏审计事实的前提下自动重建。

`20260904_21` 在增加约束前只统计并拒绝既有跨归属记录，不输出客户 ID，也不猜测修复：Turn 必须与同一 Agent 的 Conversation、同一 Conversation 的用户/助手 Message 一致；上传任务的资产版本必须同时匹配 asset 和 tenant。它还为 `ConnectorBinding` 增加 JSONB `structure_profile`、受 SHA-256 check 约束的 `structure_fingerprint`。PostgreSQL 运行角色对 `agent_turn_runs` 和 `managed_upload_runs` 仅保留 `SELECT/INSERT/UPDATE`，对 append-only `agent_turn_events` 仅保留 `SELECT/INSERT`，不再具有这些台账的 `DELETE` 权限。

`20260904_22` 增加 `assistant_request_runs`，并以 tenant/user/thread/message 复合外键闭合请求、会话和消息的归属。带附件消息、助手占位回复与执行 intent 在同一事务中落库；worker 使用 lease generation/token、续租和最终 fencing，浏览器刷新或 API 进程重启后可恢复。运行角色对该台账只有 `SELECT/INSERT/UPDATE`，没有 `DELETE` 或 DDL 权限。

`20260905_23` 允许新语义映射只绑定建模 Dataset Schema，并将旧运行绑定降为兼容锚点；升级时拒绝无法闭合 schema/entity/relation 归属的存量行。发布和运行读取规范化的映射快照，不能通过修改当前 mapping 或 Head 指针改变既有定义。该 revision 的 downgrade 仅在不存在 schema-first 映射/关系映射时允许，否则会主动拒绝把无法表示的契约压回旧模型。

`20260905_24` 为 `managed_upload_runs` 和 `assistant_request_runs` 增加 tenant-scoped `parent_run_id` 复合外键与“每个父任务一个直接子重试”的唯一约束。助手线程删除会级联其请求重试链；受管上传父任务继续受审计引用保护。旧失败/取消任务不会被重置，重试总是形成新的任务身份、revision 和 lease 世代。只要任一表仍存在子重试，downgrade 就会主动拒绝，避免静默丢失 lineage。

发布前必须从 Alembic 读取实际 single head，并首选运行仓库提供的隔离往返脚本；它会创建唯一的 `ontology_migration_verify_*` 临时数据库，验证 head 的可逆边界、运行角色权限、受限函数和审计字段，并在 `finally` 中清理临时库：

```powershell
python scripts/verify_alembic_roundtrip.py
python scripts/verify_postgresql_runtime.py
```

手工迁移往返只允许用于已经确认隔离、未运行附件到期清理的数据库副本，绝不能指向 live 或共享数据库。`verify_postgresql_runtime.py` 随后以只读方式验证当前部署库、MinIO 和可选 Redis 的运行边界，不替代隔离迁移往返。

迁移回退按以下边界 fail closed：

- `10` downgrade 检测到同一场景内不同能力使用相同 `port_key` 时，拒绝压回旧的场景级唯一键，不能静默丢端口；
- `11` downgrade 检测到已有历史版本完成物理载荷分离时拒绝，因为无法凭空恢复已删除的对象；所以往返演练必须使用尚未运行到期清理的数据库副本；
- `12` downgrade 会删除结构化的 `withdrawn_at/withdrawn_by_user_id/withdraw_reason` 字段，只能在明确接受丢失这部分撤下审计结构的回滚窗口执行；
- `20260904_19` downgrade 会删除上传任务、状态、lease 和错误台账，只能在确认没有待上传/处理中任务并明确接受该审计事实丢失时执行；
- `20260904_20` downgrade 始终拒绝；只能从备份建立新的前迁移环境，不能把污染元数据或已撤回 Release 静默恢复；
- `20260904_21` 可回退到 `20`，但会删除新增归属约束和 Connector 结构轮廓，并恢复 `18/19` 曾授予的运行角色权限；它不能跨越 `20` 的不可逆边界；
- `20260904_22` 可回退到 `21`，但会删除所有全局顾问请求状态、lease 和错误台账及新增复合约束，只能在确认没有待处理请求并接受审计事实丢失时执行。
- `20260905_23` 只有在不存在未绑定旧 `ScenarioDatasetBinding` 的 schema-first 语义映射和关系映射时才可回退；否则主动失败，不能猜测一个运行数据绑定补齐建模契约；
- `20260905_24` 只有在两类任务都不存在任何 `parent_run_id` 非空的子重试时才允许回退；否则主动失败。回退后 `23` 的映射契约仍保留。

### 8.2 目录回填

管理权限主体使用以下控制 API：

```text
POST /api/platform/migrations/legacy-catalog/start
GET  /api/platform/migrations/legacy-catalog
POST /api/platform/migrations/legacy-catalog/run
POST /api/platform/migrations/legacy-catalog/pause
POST /api/platform/migrations/legacy-catalog/resume
POST /api/platform/migrations/legacy-catalog/retry
```

回填基于 `PlatformMigrationRun` 和内容 checkpoint，可暂停、重试和幂等重跑。只有可证明的受管文件摘要、目录关系、显式角色和精确字段映射会被转换；不确定角色只进入报告，不会猜测为运行输入。存量 Agent 的历史模式字段和迁移证据可以保留，但不能继续执行历史运行路径。

### 8.3 Agent 历史模式退役

新建 Agent 以及可执行的存量 Agent 都必须使用 `capability_only`。`legacy`、`shadow` 和 `prefer_capability` 只作为存量数据库值或历史审计事实保留；运行适配器对这些模式统一返回 `historical_runtime_disabled`，不会 fallback 到旧工具路径。创建接口拒绝历史模式，通用更新接口也不能借字段修改绕过该边界。当前没有公开的 Agent 灰度、回退或 shadow 验证路由；要恢复存量 Agent，必须先通过受控迁移把它转换为完整的 `capability_only` 定义，而不是重新启用旧执行器。

### 8.4 场景下线与历史保留

场景下线分为“退役发布”和“退役场景”两个显式步骤。先对每条尚未退役的发布执行：

```http
PATCH /api/scenario-releases/{release_id}
Content-Type: application/json

{"action": "retire", "expected_revision": 2}
```

`expected_revision` 使用当前发布返回的修订号。所有正式 Release 退役后，再执行：

```http
DELETE /api/scenarios/{scenario_id}
```

发布命令使用 revision 检查并发冲突；重试前读取当前状态，已完成操作无需重复提交。`GET /api/scenarios?include_retired=true` 可以列出已退役场景，`GET /api/scenarios/{scenario_id}` 继续返回只读历史定义；外部新发现/新调用、Agent 新会话、顾问新消息及其他治理写入都会失败。普通 `DELETE` 永远不会删除目录资产、MinIO 对象、Release、Snapshot 或历史调用；物理清除必须由未来独立的留存策略和审批流程完成。

## 9. 安全与运维基线

- PostgreSQL 是控制面唯一关系数据库；MinIO 保存不可变文件和数据版本；DuckDB 只做受限只读查询。
- 所有目录、绑定、调用、Receipt 和迁移 API 都进行租户隔离与权限检查，跨租户引用在解析阶段失败。
- 公共 API/MCP manifest、新版 capability contract 和 fingerprint 不包含客户行值、凭据或物理连接信息。Receipt 的平台控制与来源元数据同样不包含这些内容；Receipt `output` 则是经过授权的业务结果，可能包含客户数据和受管逻辑引用，必须由输出 Schema、属性 ACL、脱敏和大小限制约束。
- 旧内部 RuntimeDefinition mapping 的 `data_source_id/table_name/column_map` 属于执行兼容边界。平台协议和 Provider 公共输出不得透出物理 DataSource ID、物理表列、对象存储坐标、连接配置或凭据，只能公开业务语义、已授权的受管目录引用和不可逆哈希。
- Workflow 和 Agent Turn 异步输入必须配置外部 key ring 后才能入队；无 key 时 fail closed。Agent 提交或重试遇到不可用的加密配置时返回安全的 `503 agent_turn_encryption_unavailable`，前端保留草稿并移除未被服务端接受的占位消息。
- Action/Workflow 的副作用继续执行预演、确认、审批、幂等和恢复语义；AI 来源不能绕过。
- Provider 错误对外稳定化，内部异常、连接串和攻击者字段值不得进入审计输出。
- 临时附件有明确过期时间；删除场景绑定不会删除共享资产，删除资产前必须通过引用保护检查。
- 场景的 `DELETE` 表示业务退役，不是物理清除：默认列表隐藏退役场景，审计读取仍可追溯，所有新写入和新调用失败；Definition、Release、目录资产、MinIO 对象和历史调用均保留。仍有 尚未退役的正式 Release 时必须先完成发布退役，才能退役场景。
- 生产部署必须使用 HTTPS，限制反向代理 Host、数据库备份和对象存储访问，并把 API key、LLM key、连接器凭据和 payload key ring 放在 Secret Manager。

## 10. 发布验收

每次升级至少执行：

```powershell
$env:PYTHONPATH=(Resolve-Path .\backend).Path
python -m pytest .\backend\tests -q
python .\backend\scripts\verify_postgresql_runtime.py
npm --prefix .\frontend test
npm --prefix .\frontend run build
```
