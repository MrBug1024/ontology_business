# 能力平台架构、迁移与接入指南

本文说明本平台升级后的稳定边界、运行模型、Provider 开发约束以及 REST、MCP、SDK 接入方式。本文面向平台研发、业务能力 Provider 开发者、企业集成团队和第三方 Agent 开发者。

本平台的职责是把业务语义和业务处理方法建设为可发现、可版本化、可治理、可审计的能力，并把这些能力交给任意 Agent 或客户端使用。平台内的 Agent 是验证客户端，不是客户最终业务终端；目录中的样本数据是建模证据、测试夹具或可治理资源，不是某个场景永久不变的最终业务数据。

## 1. 稳定架构边界

### 1.1 三层模型

```text
Definition plane
  Ontology + Function/Action/Workflow + CapabilityPort + Schema + policy
  形成不可变 Definition hash

Deployment plane
  Definition + environment + release + scenario defaults + connector binding
  形成 deployment fingerprint

Invocation plane
  Actor + typed inputs + managed reference overrides + confirmation/idempotency
  Head 立即固定为 Version，形成 data-context fingerprint 和 Receipt
```

- 新版 capability contract 描述能力是什么、需要什么，不保存客户某一批数据的 ID、数据库凭据、物理表名或临时附件。兼容期内旧 `RuntimeDefinition` 的 mapping 仍可能携带 `data_source_id/table_name/column_map`；这些字段属于内部执行兼容边界，不进入公共 REST/MCP manifest 或 Receipt 的平台控制元数据，Provider 对外输出也必须将它们投影为语义字段、受管引用或哈希。
- `Deployment` 说明某个 Definition 在 `dev/staging/prod` 中如何解析逻辑 binding key、稳定参考数据和连接器。
- `Invocation` 提交当前业务请求。文本、结构化参数和本次受管数据引用都属于调用输入，更换数据不要求重新建模或重新发布。

三个身份必须分开使用：

| 身份 | 变化原因 | 用途 |
| --- | --- | --- |
| `definition_hash` | 本体、能力契约、端口、Provider 版本或配置变化 | 判断业务能力版本是否变化 |
| `deployment_fingerprint` | Release、环境绑定或连接器身份变化 | 判断部署解析是否变化 |
| `data_context_fingerprint` | 本次最终固定的数据版本或连接器签名变化 | 判断本次调用实际用了什么数据 |

因此，同一个 Definition 先后处理数据版本 A 和 B 时，`definition_hash` 必须相同，`data_context_fingerprint` 必须不同。

### 1.2 数据不是必选前置条件

能力端口按用途表达数据角色：

- `modeling_evidence`：帮助理解字段、结构、关系和业务含义，不进入生产运行绑定。
- `test_fixture`：用于确定性验证和回归，不自动成为客户运行数据。
- `invocation_input`：每次调用提供的当前数据或文档。
- `reference`：可复用参考知识，可按环境固定或跟随受管版本。
- `rules`：规则表、阈值或政策版本，发布门禁必须验证其绑定。
- `output`：能力产物，不作为输入反向固化。

没有数据端口的能力是完整、合法的能力。它可以只接收文本或结构化参数；readiness 不得因为缺少 `DataSource`、`Dataset` 或 `Mapping` 而失败。

### 1.3 运行输入解析

运行输入只接受受管引用：`DatasetVersion`、`DatasetHead`、`AssetVersion` 或受信 `ConnectorBinding`。解析器按以下优先级确定每个端口：

1. 本次调用的 managed input override。
2. 当前环境的场景默认绑定。
3. 端口允许连接器且不存在数据集默认绑定时，解析当前环境的受信 `ConnectorBinding`。
4. 缺少非必填端口时保持为空；缺少必填端口时返回结构化 readiness/validation 错误。

`release_pinned` 不是第三个回退来源，而是一项约束：它禁止调用覆盖，并要求场景默认绑定为 pinned `DatasetVersion`；发布门禁会验证该版本已就绪。

`DatasetHead` 只用于选择，调用开始时立即固定为不可变 `DatasetVersion`。调用过程中不会跟随 Head 漂移。目录 Head 更新支持 `expected_dataset_version_id` compare-and-set，陈旧写入会被拒绝。

`managed_inputs` 只接受固定的受管 selector，不能提交连接串、密码、SQL、物理表名、MinIO 路径或 import path。Provider Definition 的 `runtime_config` 顶层也只接受 `provider_key/provider_version/provider_config`；平台递归拒绝 `provider_config` 中的敏感键名，以及明显包含 SQL、连接 URI、凭据赋值、连接参数或绝对物理路径的字符串。该扫描是通用安全门禁，不会猜测所有领域纯值的业务含义，因此 Provider 仍必须对完整 `provider_config` 和普通 typed `inputs` 使用封闭 Schema，明确排除未声明字段、凭据、物理查询字段和连接配置。连接器只通过服务器已登记的 `binding_key` 解析；Receipt 的平台身份字段只返回安全身份和哈希，Provider 输出的数据边界见 5.6 节。

## 2. 统一执行链路

REST、MCP、SDK 和验证 Agent 使用同一个应用服务和 `CapabilityInvoker`：

```text
protocol adapter
  -> authenticate Actor and scopes
  -> resolve immutable Definition and Deployment
  -> resolve and pin RuntimeDataContext
  -> validate schema, readiness, ACL and idempotency
  -> resolve trusted CapabilityProvider
  -> execute / preview / confirm
  -> persist CapabilityInvocation + RunInputBinding
  -> return protocol-neutral Receipt
```

协议适配器只负责认证和协议转换，不实现业务分支。统一内核负责：

- 租户、角色、scope 和场景 ACL；
- 输入 JSON Schema、受管引用和期望 hash 校验；
- 无副作用调用、预演、确认、幂等和中断恢复；
- 调用主体、来源、数据版本和证据审计；
- 输出脱敏、错误稳定化和 Receipt 查询。

副作用能力必须先 `preview`，再把服务器签发的确认票据原样用于 `confirm`，并提供幂等键。Provider 向下游传播的是平台派生的执行键，不能直接传播调用者原始幂等键。

## 3. 能力定义与发布

一个可发布能力至少包含：

1. 稳定的能力 key、名称和说明；
2. 输入、输出 JSON Schema；
3. 所需数据端口及其角色、媒介、必填性、基数和 binding policy；
4. 权限、副作用、确认和幂等策略；
5. 内置执行器类型，或显式的受信 Provider key、版本和纯值配置；
6. 校验证据和候选治理状态。

AI 和人工创建的候选进入同一质量状态机。来源不决定是否可发布；确定性校验、冲突、依赖闭包和风险策略决定晋级资格。Action 晋级为正式定义不等于自动激活。

候选治理使用同一组控制面 API，业务专家验证质量证据，而不是因为来源为 AI 就永久把模型视为不可发布草稿：

```text
GET   /api/scenarios/{scenario_id}/model-drafts
POST  /api/scenarios/{scenario_id}/model-drafts
PATCH /api/scenarios/{scenario_id}/model-drafts/{draft_id}
POST  /api/scenarios/{scenario_id}/model-drafts/{draft_id}/revalidate
POST  /api/scenarios/{scenario_id}/model-drafts/{draft_id}/promote
POST  /api/scenarios/{scenario_id}/model-drafts/promote-batch
```

人工候选、顾问候选和导入候选都先处于禁用的工作副本。编辑、重新校验和晋级请求必须携带当前 `expected_revision`；陈旧请求返回冲突，不会覆盖他人的新版本。重新校验由服务器生成 `validation_status`、`promotion_eligible`、`promotion_blockers` 和 `quality_fingerprint`。单条晋级复用批量晋级路径；批量操作要么全部形成正式定义，要么一个都不落库。任何 blocker、依赖不闭合、revision 漂移或正式化预检失败都会阻止整个批次。Action 即使晋级成功仍保持 `inactive`，必须经过独立激活治理。

`dev` 可解析 live definition；`staging/prod` 必须使用 Release 中的不可变快照。发布后修改 ORM 行、嵌套 JSON、端口或绑定不会改变已经解析的当前 deployment；只有重新解析或发布新版本才读取新状态。

## 4. Provider 开发规范

### 4.1 适用范围

以下逻辑应进入独立 Provider，而不能进入 Agent、REST、MCP 或调用内核：

- 行业字段、专用算法和业务规则；
- 场景专用工具、确定性统计、证据解释与 grounding；
- 历史工具名或 namespace 兼容；
- 对特定数据逻辑模型的解释。

Provider 包位于 `backend/app/providers/<provider_name>/`。平台启动时通过 `trusted_capability_providers()` 显式注册代码中安装的精确 `(provider_key, provider_version)` 对象，随后封闭默认注册表；数据库只能保存受信 key 和版本，不能注册代码、指定模块路径或动态导入实现。新增或卸载 Provider identity 必须通过受信代码部署完成。

### 4.2 标准接口

Provider 实现协议无关的 `CapabilityProvider`：

```python
class ExampleProvider:
    provider_key = "trusted.example"
    provider_version = "1.0.0"

    def contract(self, capability, deployment):
        return {
            "input_schema": {
                "type": "object",
                "properties": {},
                "additionalProperties": False,
            },
            "required_roles": [],
            "required_scopes": [],
            "side_effect": False,
            "requires_confirmation": False,
            "idempotency_required": False,
        }

    def bind_invocation(self, db):
        # 返回请求局部对象，不修改注册表单例。
        return ...

    def invoke(self, request, actor, deployment, data_context):
        # 只使用已验证 Actor、冻结 Definition 和不可变 RuntimeDataContext。
        return {...}
```

可选的 `preview()` 和 `recover()` 分别用于副作用预演和中断调用的无副作用对账。需要兼容旧验证 Agent 时，Provider 可实现 `bind_agent_runtime()`；不适用于当前 Agent 上下文时返回 `None`，适用时返回请求局部的 `BoundAgentProvider`。完整协议为：

```python
class BoundExampleProvider:
    provider_key = "trusted.example"
    provider_version = "1.0.0"

    def agent_tools(self):
        # Sequence[AgentToolSpec]
        ...

    def execute_agent_tool(self, name, arguments):
        ...

    def authorize_historic_tool_result(self, name, arguments, result):
        # 仅认可仍符合当前 Provider 契约的历史结果。
        ...

    def match_legacy_capability(self, name, arguments, result):
        # LegacyCapabilityMatch | None；证明 alias、能力目标、typed inputs 和比较结果。
        ...

    def normalize_capability_shadow_result(self, match, result):
        # 将 capability 输出投影为可与 legacy 结果确定性比较的 JSON 值。
        ...

    def verify_shadow_data_context(self, match, data_context):
        # 返回安全 linkage hash；上下文不匹配时返回 None。
        ...

    def prepare_grounding(self, user_message):
        ...

    def ground(self, user_message, tool_outcomes, prepared):
        # GroundingResult
        ...
```

`AgentToolSpec`、工具执行、历史结果授权、legacy/capability 等价证明、shadow 结果规范化、数据上下文核验和 grounding 的业务判断都由 Provider 自己实现。Agent 主循环只理解这些通用协议，不能识别该 Provider 的业务字段、namespace 或工具名。绑定对象的 `provider_key/provider_version` 还必须与其注册 Provider 精确一致。

### 4.3 Definition 绑定

Provider 能力使用 `runtime_kind="provider"`，配置必须且只能包含以下三项：

```json
{
  "runtime_kind": "provider",
  "runtime_config": {
    "provider_key": "trusted.example",
    "provider_version": "1.0.0",
    "provider_config": {
      "logical_contract": "example/v1"
    }
  }
}
```

`provider_key`、`provider_version` 和 `provider_config` 都进入 Definition 身份。`provider_config` 只能保存可发布的纯值语义配置；平台会扫描敏感键名和明显危险的字符串值，Provider 仍必须按自己的封闭配置契约校验全部语义与未声明字段。扫描通过不代表某个值已经获得业务授权。

注册表以 `(provider_key, provider_version)` 作为完整的 `ProviderIdentity`，同一个 key 可以显式安装多个版本。Definition 只解析与其声明完全相同的 identity；这里不是 semver 范围匹配，也不会在缺少目标版本时回退到同 key 的最新版。精确版本未安装或绑定对象版本不一致时，能力发现或调用会以安全错误失败，而不会让新实现静默解释旧 Definition。升级时应先并行安装新版本、发布引用它的新 Definition/Release，确认旧 Release 退役后再卸载旧版本。

### 4.4 Provider 验收清单

- Provider 单元测试覆盖 contract、输入 Schema、版本拒绝、ACL 和安全错误。
- 有数据能力至少验证两个受管版本 A/B，结果和 provenance 只引用本次版本。
- 零数据能力验证不创建 DataSource、Dataset、Mapping 仍可调用。
- Agent、REST、MCP 的输出语义及 Definition/Deployment/DataContext provenance 一致。
- 兼容 alias 只存在于 Provider 自有 manifest。
- 架构扫描确认平台内核无行业名、字段名和固定工具名。

### 4.5 内置执行器的数据上下文边界

普通 JSON 参数与受管数据端口是两类不同输入。当前执行器支持矩阵如下：

| 执行器 | `inputs` 类型化参数 | 非空 `RuntimeDataContext` |
| --- | --- | --- |
| builtin Function | 支持 | 当前拒绝 |
| builtin Action | 支持，保留预演/确认/幂等 | 当前拒绝 |
| builtin Workflow | 支持，异步载荷加密恢复 | 当前拒绝 |
| trusted Provider | 按 Provider contract | 必须显式消费、校验并形成 provenance |

因此，声明了受管数据端口的能力必须使用实现相应 typed materializer 的受信 Provider。平台不会因为端口存在，就让内置执行器静默忽略数据上下文并返回看似成功的结果；尚未支持时统一 fail closed。

## 5. REST v2 接入

### 5.1 创建凭据

管理员通过 `POST /api/developer/api-keys` 创建带以下 scope 的 API key：

```json
{
  "name": "enterprise-agent",
  "scopes": ["capabilities:read", "capabilities:invoke", "assets:write"]
}
```

原始 `ont_sk_...` token 只在创建响应中返回一次。生产环境通过 HTTPS 传入 `X-API-Key`，不得放入 URL、日志或前端持久存储。

凭据管理端点为 `GET /api/developer/api-keys`、`POST /api/developer/api-keys` 和 `DELETE /api/developer/api-keys/{key_id}`。列表与吊销响应只包含元数据，不会再次返回原始 token。只做零数据或引用既有目录版本的客户端不需要 `assets:write`；只有需要提交新文件的集成才授予该独立 scope。

### 5.2 发现场景、能力与受管输入选项

第三方 Agent 不需要从平台 UI 或人工配置中取得 `scenario_id`。先用同一把 API key 获取当前主体有权读取的活动场景：

```http
GET /api/external/v2/scenarios
X-API-Key: ont_sk_...
```

响应只包含逻辑场景的 `id/name/description/industry`，按 API key 所属租户和场景 read ACL 过滤，并排除已退役场景；不会返回租户内部配置、数据源或物理存储信息。选定场景后发现能力：

```http
GET /api/external/v2/scenarios/{scenario_id}/capabilities?environment=prod
X-API-Key: ont_sk_...
```

当前 REST v2 可发现和调用的 `kind` 为 `function`、`action`、`workflow`。响应给出 `kind`、`key`、输入/输出 Schema、数据端口、`readiness.ready/issues`、`definition_hash` 和 `deployment_fingerprint`。公开 issue 的 `axis` 为 `definition`、`validation` 或 `runtime`；客户端应在调用时回传两个期望 hash，以防发现和执行之间发生部署变化。

每个能力响应中的 `data_ports` 只包含明确归属当前 `{kind, key}` 的端口。客户端不得读取或猜测同场景其他能力的端口：文本、数字、普通对象和数组始终按 `input_schema` 放入 `inputs`，不能为了提交参数而先创建资产。只有 `direction=input` 且 `allow_override=true` 的端口才能出现在 `managed_inputs`，selector 类型还必须属于该端口返回的 `binding_kinds`；`release_pinned` 或 `allow_override=false` 的端口不得按次覆盖。

对允许逐次覆盖的端口，客户端通过当前能力和端口限定的目录获取可用逻辑引用，而不是调用控制面数据源 API 或猜测内部 ID：

```http
GET /api/external/v2/scenarios/{scenario_id}/capabilities/{kind}/{capability_key}/ports/{port_key}/managed-input-options?environment=prod&limit=100&offset=0
X-API-Key: ont_sk_...
```

选项目录再次验证场景 ACL、冻结 Definition、当前 Deployment、端口归属、`allow_override` 和 `binding_kinds`。响应带分页信息、`definition_hash`、`deployment_fingerprint`、端口允许的 selector 类型，以及可以直接放入调用请求的 `items[].managed_input`（含服务器校验过的 selector 与 `expected_signature`）。客户端应原样提交该对象并回传两个身份 hash。响应不会暴露 DataSource ID、对象路径、物理表列、连接目标、连接配置或凭据。

### 5.3 零数据能力调用

```http
POST /api/external/v2/scenarios/{scenario_id}/capabilities/function/{capability_key}/invoke
X-API-Key: ont_sk_...
Content-Type: application/json

{
  "environment": "prod",
  "mode": "execute",
  "inputs": {
    "request": "整理这些零散需求并输出验收标准",
    "fragments": ["需要权限隔离", "支持批量导入"]
  },
  "managed_inputs": [],
  "expected_definition_hash": "<discovery response>",
  "expected_deployment_fingerprint": "<discovery response>"
}
```

零数据能力不需要构造空 DataSource 或伪造 Mapping。

### 5.4 每次提供不同数据

```json
{
  "environment": "prod",
  "mode": "execute",
  "inputs": {"threshold": 0.8},
  "managed_inputs": [
    {
      "port_key": "records",
      "dataset_version_id": "<governed-version-b>",
      "expected_signature": "<optional-current-signature>"
    }
  ],
  "expected_definition_hash": "<discovery response>",
  "expected_deployment_fingerprint": "<discovery response>"
}
```

支持的 selector 为 `dataset_version_id`、`dataset_head_id`、`asset_version_id`、`artifact_id` 或 `binding_key`，每个端口必须且只能提交一个。当前 `artifact_id` 是 `DataAssetVersion.id` 的兼容别名，不是第二套 Artifact 权威。使用 Head 时，精确的最终 Version 保存在内部 `RunInputBinding` 和调用审计中，Receipt 顶层使用 `data_context_fingerprint` 表达统一的数据上下文身份。若能力的输出契约需要可核验 provenance，Provider 可以返回当前主体已获授权的受管 `reference_id/version_id/signature`；这些是目录逻辑引用，不是物理 DataSource、对象存储位置或连接配置。

### 5.5 文档和临时附件

二进制内容不能直接塞入 invocation JSON。第三方 Agent 使用独立的 `assets:write` scope 调用：

```http
POST /api/external/v2/assets/upload
X-API-Key: ont_sk_...
Content-Type: multipart/form-data

file=@requirements.docx
name=current-requirements
expires_in_seconds=3600
```

外部 multipart 只接受：

- `file`：CSV、XLSX 或支持解析的文档；
- `name`、`description`：可选逻辑元数据；
- `expires_in_seconds`：可选；临时附件默认 24 小时，可在允许范围内显式缩短或延长。

平台按当前 API key 的租户在服务端解析受管上传桶，并强制 `purpose=invocation_attachment`。请求不能提交 `file_bucket_id`、桶名、对象路径、endpoint、前缀、连接参数或凭据；未知字段也会失败。`MAX_UPLOAD_BYTES` 默认是 50 MiB，反向代理也应配置不低于 multipart 开销且不高于组织允许值的请求体上限；超限在 multipart 解析前返回 `413`。临时附件默认保留 24 小时，调用方可在 300 秒到 7 天之间选择 TTL。

文件经过格式、签名、大小和压缩容器检查后形成内容身份、hash 与审计引用不可变的 `DataAssetVersion`。在有效期内重复上传相同内容会返回同一版本并令 `created=false`；到期后，逻辑版本保留并转为 `retired`，物理 `BucketFile`/MinIO 载荷通过删除 Outbox 分离和清理，历史 `RunInputBinding` 仍能追溯内容 hash，但该版本不能用于新调用。到期后再次上传相同内容会形成新的版本身份。响应只返回 `purpose/temporary/expires_at/created` 以及嵌套的 `{ "asset": {...}, "version": {...} }`，不返回物理存储身份。随后把 `response.version.id` 作为 `asset_version_id` 提交到该能力自己的文档端口。

第一方登录控制面仍可使用 `POST /api/catalog/uploads`，由已获目录写权限的用户显式选择当前租户受管文件桶。两条上传路径共用相同的原子目录写入、内容去重、生命周期和失败清理服务，但外部路径永远不能选择物理桶。

### 5.6 Receipt

调用返回 `invocation_id`、状态、三个身份 hash、输出、审计引用和确认信息。可使用：

```http
GET /api/external/v2/invocations/{invocation_id}
X-API-Key: ont_sk_...
```

Receipt 查询要求 `capabilities:read` scope、同租户、当前场景 read ACL，并且 `principal_type/principal_id` 与原调用完全相同。对于外部 REST/MCP 调用，`principal_id` 是 API key ID，而不是它所属的用户 ID；因此同一把 key 可以跨 REST/MCP 查询自己的调用，但轮换后的新 key 不能查询旧 key 创建的 Receipt。

Receipt 中的数据分为两类：

- 平台控制与来源元数据：调用身份、三个 fingerprint、状态、确认信息和审计引用，不包含凭据、物理连接配置或未授权引用。
- `output`：Provider 按能力输出契约产生的授权业务结果，可能包含客户提交内容或派生业务数据，也可能包含已授权的受管逻辑引用；它必须经过输出 Schema、属性 ACL、脱敏和大小限制，不得包含 DataSource ID、物理表列、对象存储坐标、连接配置或凭据。

## 6. MCP 接入

通用 MCP 与 REST v2 使用同一个 `ont_sk_...` 凭据和统一 Invoker：

```json
{
  "mcpServers": {
    "business-capabilities": {
      "type": "http",
      "url": "https://platform.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ont_sk_..."
      }
    }
  }
}
```

提供三个通用工具：

- `list_capabilities`：按 `scenario_id` 和 environment 发现契约，返回 `{ "capabilities": [...] }`；
- `invoke_capability`：对 `function/action/workflow` 提交 typed inputs、managed inputs、模式和期望 hash；
- `get_capability_receipt`：查询统一回执。

当前 MCP 工具集不提供场景目录和受管输入选项目录。纯 MCP 客户端需要由部署方提供已授权的 `scenario_id` 和逻辑受管引用；需要自主引导的客户端应先使用同一凭据调用 REST v2 的场景与端口选项端点，或直接使用 Python SDK，再通过 MCP 调用能力。MCP 不会退化为暴露物理数据源目录来填补这一边界。

MCP 网关不承载 multipart 二进制上传。需要提交新文档时，客户端先用同一 `ont_sk_...` 凭据和独立 `assets:write` scope 调用 REST `/api/external/v2/assets/upload`（或 SDK 的 `upload_invocation_attachment`），再把返回的 `version.id` 作为 `asset_version_id` 交给 MCP `invoke_capability`。因此 MCP 是能力调用协议，受管附件上传是配套 REST 数据入口；不具备 HTTP 上传能力的纯 MCP 客户端不能提交新二进制文件。

同一个 `/mcp` 网关还会发布兼容工具 `invoke_agent`，因此工具发现结果不止上述三个名称：`ont_sk_...` 只授权通用 capability 工具，旧 `agt_sk_...` 发布凭据只授权它绑定的 `invoke_agent`。`invoke_agent` 不是新集成的主路径；新客户端不应依赖平台 Agent ID、固定数据源列表或业务专用 MCP 工具名。

## 7. Python SDK

`backend/sdk/ontology_platform_sdk.py` 是本仓库随源码交付的辅助模块，并非已发布到公共包仓库的安装包；从 `backend` 目录运行集成代码，或把仓库的 `backend` 目录加入 `PYTHONPATH`。它把两个协议版本作为独立接入入口：`OntologyPlatformClient` 使用 `/api/external/v1` 做旧的只读场景/对象访问，`CapabilityClient` 使用 `/api/external/v2` 做场景/能力发现、受管选项选择、附件上传、调用和 Receipt 查询。两者不能共用同一个 base URL；`CapabilityClient` 不复制 Provider 逻辑：

```python
from sdk import CapabilityClient

with CapabilityClient(
    "https://platform.example.com/api/external/v2",
    "ont_sk_...",
) as client:
    scenario = client.list_scenarios()[0]
    contract = client.list_capabilities(scenario["id"], environment="prod")[0]
    uploaded = client.upload_invocation_attachment(
        "requirements.docx",
        document_bytes,
        content_type="application/vnd.openxmlformats-officedocument.wordprocessingml.document",
        expires_in_seconds=3600,
    )
    receipt = client.invoke_capability(
        scenario["id"],
        contract["kind"],
        contract["key"],
        environment="prod",
        inputs={"request": "分析当前输入"},
        managed_inputs=[{
            "port_key": "requirements",
            "asset_version_id": uploaded["version"]["id"],
        }],
        expected_definition_hash=contract["definition_hash"],
        expected_deployment_fingerprint=contract["deployment_fingerprint"],
    )
    same_receipt = client.get_invocation_receipt(receipt["invocation_id"])
```

副作用能力必须显式完成预演和确认，不能把 `execute` 当作旁路：

```python
action_contract = client.get_capability(
    scenario["id"], "action", "capability-key", environment="prod"
)
preview = client.invoke_capability(
    scenario["id"], "action", "capability-key",
    environment="prod", mode="preview", inputs={"request_id": "R-1001"},
    expected_definition_hash=action_contract["definition_hash"],
    expected_deployment_fingerprint=action_contract["deployment_fingerprint"],
)
confirmed = client.invoke_capability(
    scenario["id"], "action", "capability-key",
    environment="prod", mode="confirm", inputs={"request_id": "R-1001"},
    confirmation=preview["confirmation"],
    idempotency_key="enterprise-agent:R-1001",
    expected_definition_hash=action_contract["definition_hash"],
    expected_deployment_fingerprint=action_contract["deployment_fingerprint"],
)
```

`CapabilityClient` 当前只支持 `function/action/workflow`。SDK 默认要求 HTTPS、拒绝 URL 凭据且不跟随带凭据重定向。本地回环联调必须显式设置 `allow_insecure_http=True`，并且目标主机必须是 localhost 或数值回环地址。

## 8. 存量迁移与回退

### 8.1 数据库迁移

按 Alembic 增量升级，不删除存量表：

```powershell
cd backend
python -m alembic -x use_admin=1 upgrade head
```

迁移 `20260827_02` 引入可恢复的 `PlatformMigrationRun/Checkpoint` 台账；`07` 增加 capability ports、invocations 和 `RunInputBinding`，`08` 增加 Agent 逐次输入审计，`09` 将异步 Workflow 输入迁移为 AES-256-GCM 加密载荷，`10` 把每个数据端口显式归属到一个 Function、Action 或 Workflow，`11` 支持临时附件到期后保留逻辑版本并分离物理载荷，`12` 增加 Release 撤下审计事实。`10` 只接受端口 `config.contract_source` 及已治理草稿解析关系作为存量归属证据；无法唯一证明的行会让迁移 fail closed，不能按名称、端口前缀或“场景只有一个能力”猜测。执行涉及既有 WorkflowRun 的 `09` 升级前，部署必须提供：

```ini
WORKFLOW_PAYLOAD_ACTIVE_KEY_ID=<active-key-id>
WORKFLOW_PAYLOAD_ENCRYPTION_KEYS={"<active-key-id>":"<urlsafe-base64-32-byte-key>"}
```

密钥只进入部署 Secret Manager，不能写入仓库、数据库或日志。轮换时先把新 key 加入 key ring，再切换 active id；旧 envelope 继续按自身的 `key_id` 解密。当前没有历史载荷 rewrap，也没有以“配置的留存期已过”替代实际删除的机制。只有确认所有引用旧 `key_id` 的现存 `WorkflowRun` 已实际删除，并且允许 downgrade 的回滚窗口也已经结束，才能移除旧 key；任一存量行仍引用它时，运行恢复、重试或 `09` downgrade 都会 fail closed。

`09` downgrade 会在事务内解密全部现存 envelope，把数据库列恢复为旧版明文输入，然后删除加密摘要列。因此它是会降低静态数据保护级别的紧急回退，不是普通无风险回滚；执行前必须确认完整历史 key ring 可用，并按明文载荷重新落实数据库访问、备份和留存保护。

当前 head 为 `20260829_12`。发布前首选运行仓库提供的隔离往返脚本；它会创建唯一的 `ontology_migration_verify_*` 临时数据库，验证 head -> `09` -> head、运行角色边界、到期附件受限函数和 Release 撤下字段，并在 `finally` 中清理临时库：

```powershell
python scripts/verify_alembic_roundtrip.py
python scripts/verify_postgresql_runtime.py
```

手工执行 `upgrade 20260829_12 -> downgrade 20260829_09 -> upgrade 20260829_12` 只允许用于已经确认隔离、未运行附件到期清理的数据库副本，绝不能指向 live 或共享数据库。`verify_postgresql_runtime.py` 随后验证当前部署库、MinIO 和 Redis 的运行边界，不替代隔离迁移往返。

迁移回退按以下边界 fail closed：

- `10` downgrade 检测到同一场景内不同能力使用相同 `port_key` 时，拒绝压回旧的场景级唯一键，不能静默丢端口；
- `11` downgrade 检测到已有历史版本完成物理载荷分离时拒绝，因为无法凭空恢复已删除的对象；所以往返演练必须使用尚未运行到期清理的数据库副本；
- `12` downgrade 会删除结构化的 `withdrawn_at/withdrawn_by_user_id/withdraw_reason` 字段，只能在明确接受丢失这部分撤下审计结构的回滚窗口执行。

### 8.3 Agent 灰度

新建验证 Agent 默认 `capability_only`。设置 `NEW_AGENT_RUNTIME_BINDING_MODE=legacy` 可回退新建默认行为，但不会重写任何存量行。

存量 Agent 的迁移是逐个、显式且有门禁的：

```text
GET  /api/agents/{agent_id}/migration
POST /api/agents/{agent_id}/migration/shadow/refresh
POST /api/agents/{agent_id}/migration/shadow/validate
POST /api/agents/{agent_id}/migration/mode
POST /api/agents/{agent_id}/migration/rollback
```

迁移必须按以下顺序前进，不能跳级：

```text
legacy -> shadow -> prefer_capability -> capability_only
```

从 `legacy` 进入 `shadow` 不要求已有比较证据；从 `shadow` 进入 `prefer_capability`，以及继续进入 `capability_only`，都要求服务器门禁已经通过。直接通用 PUT 不能改变模式或绕过门禁。`rollback` 可从任意模式恢复 `legacy`，并记录原因和幂等键；它不会修改新建 Agent 的部署默认值。

每次切换前先读取 `GET /api/agents/{agent_id}/migration`，以服务端返回的 `gate` 和 `runtime_binding_mode` 为权威。进入下一阶段和一键回退的请求分别为：

```json
{
  "target_mode": "shadow",
  "reason": "开始受控影子验证",
  "idempotency_key": "agent-x-to-shadow-1"
}
```

```json
{
  "reason": "结果门禁退化，恢复 legacy",
  "idempotency_key": "agent-x-rollback-1"
}
```

客户端本地计算的 hash、行数或结果相等不能作为迁移门禁证据。

`shadow` Agent 的在线请求仍执行 legacy 路径，同时持久化 typed inputs 的安全 hash/结构轮廓、managed reference selector 意图、能力目标和 Definition/Deployment/DataContext 身份快照；原始 typed input 值不会复制到该审计快照。它不会自动双跑 capability。`shadow/refresh` 只把这些服务器快照回填为诊断 observation，记录 `gate_eligible=false`，不能单独推动切换。

可计入门禁的证据由 `shadow/validate` 生成。请求只提交原始调用事实，而不提交比较 hash、Schema、行数或结果指标：

```json
{
  "source_message_id": "<finalized-shadow-assistant-message>",
  "legacy_tool_result_id": "<persisted-tool-result-id>",
  "capability_kind": "function",
  "capability_key": "<capability-key>",
  "inputs": {"request": "<same-structured-input>"},
  "managed_inputs": []
}
```

服务器要求 Agent 当前处于 `shadow`，来源消息属于该 Agent、已完成且实际选择 legacy 路径，没有使用 fallback；提交的输入、受管 selector 和能力目标必须与持久化快照完全一致，Definition/Deployment/DataContext 也不能漂移。服务器会重新构建当时的 legacy 语义上下文，并通过 Provider 自有的历史结果授权与 capability 匹配协议，证明工具名、参数和结果确实归属于同一个能力目标及 typed inputs；Provider 还必须核验本次 RuntimeDataContext 与该 legacy 结果对应的数据上下文，平台内核不包含任何业务工具名映射。验证器随后只执行无副作用且不要求确认的 ready capability，由同一 Provider 将两侧结果投影为确定性可比的 JSON 值后在内存中比较；台账只保存归属 ID、linkage hash、可重算的 `data_equivalence_hash`、结果 hash 和聚合行数，不保存两侧原始结果。

当前门禁使用最近两条 `gate_eligible=true` observation，要求 capability context 完整、没有 fallback、Schema 和结果 hash 相同，并在两侧都是列表时要求行数完全一致。门禁每次评估都会从真实 Message、成功的 Agent Invocation、`RunInputBinding` 和当前受信 Provider 重新生成包括 `data_equivalence_hash` 在内的证据；客户端无法通过 `shadow/refresh`、篡改 checkpoint 标志或请求字段伪造这些比较事实。

### 8.4 场景下线与历史保留

场景下线分为“撤下可执行发布”和“退役场景”两个显式步骤。对存在活动 Release 的环境先执行：

```http
POST /api/scenarios/{scenario_id}/releases/prod/withdraw
Content-Type: application/json

{"confirmed": true, "reason": "业务能力正式下线"}
```

预发布环境使用同一路径的 `staging`。所有 staging/prod 活动 Release 撤下后，再执行：

```http
DELETE /api/scenarios/{scenario_id}
```

撤下和退役命令均可安全重试。`GET /api/scenarios?include_retired=true` 可以列出已退役场景，`GET /api/scenarios/{scenario_id}` 继续返回只读历史定义；外部新发现/新调用、Agent 新会话、顾问新消息及其他治理写入都会失败。普通 `DELETE` 永远不会删除目录资产、MinIO 对象、Release、Snapshot 或历史调用；物理清除必须由未来独立的留存策略和审批流程完成。

## 9. 安全与运维基线

- PostgreSQL 是控制面唯一关系数据库；MinIO 保存不可变文件和数据版本；DuckDB 只做受限只读查询。
- 所有目录、绑定、调用、Receipt 和迁移 API 都进行租户隔离与权限检查，跨租户引用在解析阶段失败。
- 公共 API/MCP manifest、新版 capability contract 和 fingerprint 不包含客户行值、凭据或物理连接信息。Receipt 的平台控制与来源元数据同样不包含这些内容；Receipt `output` 则是经过授权的业务结果，可能包含客户数据和受管逻辑引用，必须由输出 Schema、属性 ACL、脱敏和大小限制约束。
- 旧内部 RuntimeDefinition mapping 的 `data_source_id/table_name/column_map` 属于执行兼容边界。平台协议和 Provider 公共输出不得透出物理 DataSource ID、物理表列、对象存储坐标、连接配置或凭据，只能公开业务语义、已授权的受管目录引用和不可逆哈希。
- Workflow 异步输入必须配置外部 key ring 后才能入队；无 key 时 fail closed。
- Action/Workflow 的副作用继续执行预演、确认、审批、幂等和恢复语义；AI 来源不能绕过。
- Provider 错误对外稳定化，内部异常、连接串和攻击者字段值不得进入审计输出。
- 临时附件有明确过期时间；删除场景绑定不会删除共享资产，删除资产前必须通过引用保护检查。
- 场景的 `DELETE` 表示业务退役，不是物理清除：默认列表隐藏退役场景，审计读取仍可追溯，所有新写入和新调用失败；Definition、Release、目录资产、MinIO 对象和历史调用均保留。仍有 active staging/prod Release 时必须先完成发布退役，才能退役场景。
- 生产部署必须使用 HTTPS，限制反向代理 Host、数据库备份和对象存储访问，并把 API key、LLM key、连接器凭据和 payload key ring 放在 Secret Manager。
