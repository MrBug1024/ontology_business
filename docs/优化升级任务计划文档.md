## 1. 文档权威与执行规则

本文件是本轮架构升级的唯一执行计划。实现过程中若设计发生变化，必须先更新本文件中的目标、任务、依赖和验收条件，再修改代码。`docs/实现计划.md` 中与本文件冲突的旧设计，由本文件覆盖。

每个任务必须使用以下状态之一：

| 状态 | 含义 |
| --- | --- |
| `TODO` | 尚未开始 |
| `IN_PROGRESS` | 正在实现，同一阶段允许并行任务 |
| `DONE` | 代码、测试、文档和验收条件均已完成 |
| `BLOCKED` | 已明确记录外部阻塞条件，不能用来代替未完成 |

状态更新规则：

1. 开始修改任务对应代码前，将任务更新为 `IN_PROGRESS`。
2. 只有任务列出的验收条件全部满足，才可更新为 `DONE`。
3. 兼容分支仍存在不代表任务未完成，但必须有明确的迁移模式、告警和删除边界。
4. 禁止为了让医保审计、AI 项目经理或任何单一场景通过而在平台内核增加行业字段、固定表名、固定工具名或场景命名空间分支。

## 2. 本轮目标

平台从“绑定固定数据源的 Agent 终端”升级为“可被任意 Agent、客户端或协议调用的版本化业务能力平台”。

本轮完成后的核心事实应为：

- 场景定义描述业务语义、能力、策略、输入输出契约和数据要求，不持有某一批客户业务数据。
- “建模资料”中的 Excel、Word、文件和数据库连接全部且仅用于理解场景、发现结构和辅助建模；默认全部可用于建模，不要求用户声明用途，也没有成为正式运行数据的路径。
- 验证 Agent 的正式业务数据只来自当前对话上传的文件和 Agent 创建/编辑页配置的业务数据库；第三方调用也必须显式提供本次受管输入或其专属连接。
- 没有固定数据源的场景可以建模、验证、发布和调用。
- 平台内的 Agent 是“验证 Agent/参考客户端”，不是能力唯一载体。
- MCP、REST、内部 Agent 和后续 SDK 都调用同一个协议无关的 `CapabilityInvoker`。
- AI 和人工只是定义来源不同；能否晋级、启用、发布由确定性校验、风险和环境策略决定。

## 3. 非目标

本轮不做以下破坏性操作：

- 不删除或重命名旧数据库字段和旧 `/data-sources` API；`Agent.data_source_ids` 仅保留线协议/数据库兼容，运行时与 UI 均忽略并清空。
- 不破坏 `/external/v1`、现有 Function/Action/Workflow 入口和 MCP `invoke_agent(message, conversation_id)`。
- 不把所有实时数据库伪造成不可变 `DatasetVersion`。
- 不在 Alembic 事务中执行大规模文件摄取或历史数据转换。
- 不允许客户端在调用请求中提交数据库连接串、凭据、任意 SQL、任意物理表名或未经治理的字段映射。
- 不因 AI 生成而跳过副作用、凭据和生产发布的安全门禁。

## 4. 目标领域模型

### 4.1 三层主模型

```text
Scenario Definition Version
  = OntologySnapshot / RuntimeDefinition
  + 对象、关系、函数、Action、Workflow、规则
  + Capability Port Contract
  + 语义映射、策略、评测要求、建模证据
  - 客户本次运行数据

Resolved Deployment
  = 已发布 Definition
  + tenant + environment
  + policy override
  + deployment fingerprint

Capability Invocation
  = Resolved Deployment
  + actor / principal
  + capability reference
  + typed inputs
  + per-call managed data references
  + idempotency / correlation / audit
```

本轮不新增第二套持久化 Release 或 Deployment 权威。`OntologyRelease` 是能力定义发布版本；`scenario_id + environment + release + 已解析绑定` 形成运行时 `ResolvedDeployment`。未来只有在出现“同一租户、同一环境、同一场景并行多部署”的真实需求后，才考虑持久化 Deployment 实体。

### 4.2 数据概念

| 概念 | 职责 | 是否属于定义 | 是否可以每次变化 |
| --- | --- | --- | --- |
| 建模 `DataSource` | 场景理解、结构画像、语义发现和建模辅助 | 否 | 可以，但永不进入正式调用 |
| Agent Runtime Connection | 在 Agent 创建/编辑时配置的正式业务数据库 | 否 | 可以，由 Agent 独占 |
| `DataAssetVersion` | 文件、对象等不可变资产版本 | 否 | 可以 |
| `LogicalDataset/DatasetVersion` | 有 Schema、版本和血缘的数据产品 | 否 | 可以 |
| `ModelingEvidence` | 帮助 AI/专家理解场景的数据证据 | 只记录引用与结构证据 | 可以 |
| `TestFixture` | 验证定义和能力的评测输入 | 只记录测试引用 | 可以 |
| `CapabilityPort` | 能力所需数据/文本/文档/事件契约 | 是 | 契约版本化，值可变化 |
| `ScenarioDatasetBinding` | 历史目录兼容元数据，仅服务建模/测试治理 | 否 | 可以，但运行解析器禁止读取 |
| `RunInputBinding` | 某次调用最终固定的数据引用 | 否，属于调用审计 | 每次不同 |
| `ExecutionArtifact` | 输入、输出和证据产物 | 否，属于调用审计 | 每次不同 |
| `OntologyInstance` | 可选业务状态源或可重建服务投影 | 否 | 可以 |

### 4.3 建模资料原则

- 用户无需给文件、文档或数据库声明“建模证据/测试夹具/参考资料”等用途。
- 场景建模默认可以读取当前租户有权访问的全部建模资料。
- 用途、角色、测试集等标签只允许作为平台内部治理元数据，不出现在主流程，也不能改变“仅建模”的硬边界。
- 若某份历史资料需要作为一次正式调用输入，调用方必须重新在当前对话上传或通过 Agent 专属业务数据库提供；平台不得复用其建模资料 ID。

### 4.4 数据端口

`ScenarioCapabilityPort` 只声明要求，不保存业务数据：

- 稳定 `key`、显示名称和描述。
- `direction`：`input | output`。
- `role`：使用统一数据角色。
- `media_kind`：`message | structured | document | dataset | connector | artifact`；scalar、object、tabular、object_set、event 等结构形态由 JSON Schema 表达，避免把传输介质与数据结构混为一类。
- JSON Schema、可选 Dataset Schema 引用和语义要求。
- 是否必填、基数、允许的绑定类型和覆盖策略。
- 保留、敏感性和审计策略。

### 4.5 正式调用输入来源

```text
1. 当前对话上传的临时受管附件。
2. 当前 Agent 创建/编辑时配置的专属业务数据库。
3. 第三方调用显式提交的本次受管数据引用或第三方 Agent 专属连接。
4. 普通自然语言和能力业务参数。
5. 必填输入仍未满足时，由 Agent 追问或返回结构化缺失说明。
```

禁止从 `ScenarioDatasetBinding`、建模 `DataSource`、`Agent.data_source_ids` 或部署进程环境变量隐式补足业务输入。审计记录不得保存凭据和未经脱敏的敏感内联数据。

## 5. 能力内核与协议边界

### 5.1 CapabilityInvoker

唯一执行入口的职责顺序：

1. 验证用户、服务或 Agent 身份。
2. 解析 Definition 与 ResolvedDeployment。
3. 校验客户端期望的 Definition hash/release pin。
4. 解析并授权 capability。
5. 计算 definition、publication、validation、invocation 四类 readiness。
6. 解析数据端口并形成不可变 `RuntimeDataContext`。
7. 校验结构化输入。
8. 通过通用执行器或已注册 Provider 执行。
9. 复用现有预演、确认、幂等、审批和审计语义。
10. 返回统一 `CapabilityInvocationReceipt`。

Invoker 不负责 Prompt 组织、MCP/HTTP 响应格式、行业字段、行业策略或物理数据查询细节。

### 5.2 CapabilityProvider

特殊业务能力通过受信任代码包实现 `CapabilityProvider`，由静态注册表或安装包 entry point 注册。数据库内容不得指定任意 Python 导入路径。

Provider 可以提供：契约补充、readiness、执行计划、执行、证据重授权和 grounding。平台内核只能按 provider key 分派，不能判断 `medical_audit` 等场景 namespace，也不能判断 `run_medical_audit` 等固定工具名。

### 5.3 协议适配器

内部验证 Agent、REST、MCP 和 SDK 只能完成：认证、协议解析、构造统一调用请求、调用 Invoker、渲染统一回执。协议层不得包含业务字段、SQL、Mapping 或 Provider 分支。

## 6. 兼容与迁移模式

所有新建和存量 Agent 统一为 `capability_only`。`legacy / shadow / prefer_capability` 仅保留为历史快照可读值，不再作为产品运行分支。迁移时清空旧 `Agent.data_source_ids`，绝不把其中的建模资料自动复制成正式业务连接；真正的实时数据库只能在 Agent 创建/编辑页重新明确配置。

## 7. 禁止业务硬编码的发布门禁

以下规则由架构测试执行，而不仅是代码评审约定：

1. `capability_invoker`、`runtime_input`、`binding_resolver`、协议路由和 Agent 主循环不得出现行业名、行业字段、固定场景 namespace 或固定 Provider 工具名。
2. 新平台 API 不接受 `DataSource.id`、物理表名、列名、SQL 或连接凭据作为调用覆盖。
3. Provider 代码放在独立能力包边界，通过通用接口注册；核心测试不得依赖某个 Provider 才能通过。
4. 至少使用一个“必填表格输入”测试能力和一个“零数据端口”测试能力验证内核；二者均以通用 fixture/Provider 注册完成。
5. Definition hash 与数据绑定 fingerprint 分离；更换数据不能改变 Definition hash。
6. 发布 manifest 不包含客户数据 ID、数据内容或明文凭据。

## 9. 依赖顺序

```text
M0 基线与护栏
  -> M1 数据端口、调用审计、目录 API
      -> M2 Release Contract、BindingResolver、CapabilityInvoker
          -> M3 Agent / REST / MCP / SDK 适配器
          -> M4 AI 候选治理
              -> M5 前端完整工作流
              -> M6 Provider 与双纵向切片
                  -> M7 回填、灰度、全量验证和交付
```

允许并行：

- `CAT-001/002/003` 可与 `RT-001/002` 并行，但 `RT-003` 必须等待目录契约稳定。
- REST、MCP 和 Agent 适配器可以并行，但都必须调用同一个已通过测试的 Invoker。
- AI 状态机和前端基础契约可以并行，但前端不得自行推断晋级资格或 readiness。

## 10. 必须通过的验收矩阵

| 场景 | 定义输入 | 运行输入 | 必须结果 |
| --- | --- | --- | --- |

## 11. 完成定义

本轮只有同时满足以下条件才算完成：

1. 所有本轮任务状态为 `DONE`，不存在用 `BLOCKED` 掩盖的核心链路。
2. 医保 A/B 数据切换与零数据项目需求分析两个相反场景均端到端通过。
3. 平台内核不含任何为上述场景增加的行业硬编码。
4. 现有兼容测试、后端全量测试、前端测试与生产构建通过。
5. 数据库增量迁移经过真实 PostgreSQL upgrade/downgrade/upgrade 验证。
6. 文档足以让第三方 Agent 通过 REST 或 MCP 调用能力，而不依赖平台前端。
