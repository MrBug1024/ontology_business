# 生产部署

本平台的生产存储边界固定为 **PostgreSQL、MinIO 和 Redis**。其中 PostgreSQL 是唯一
关系型数据库和控制面权威来源；MinIO 保存原始上传、数据集与证据对象；Redis 只保存可重建的
短期缓存。不要再部署或挂载 SQLite 文件，也不要配置 `/app/data/platform.db` 或 `/app/data`
卷来保存平台数据。PostgreSQL 必须使用具备备份和恢复能力的外部持久化实例，MinIO Bucket 也
必须由外部持久化存储和生命周期策略保障。

生产 Compose 入口为仓库根目录的 `compose.production.yml`，不创建 PostgreSQL、Redis 或
MinIO 容器。它假定这三项服务已经由受管基础设施或独立运维栈提供。

## 拓扑与职责

```text
Browser
  -> web (Nginx: static Vue files, /api and /mcp proxy)
       -> api (Uvicorn workers: HTTP / SSE only)
       -> worker (one logical durable-job consumer)

api / worker -> external PostgreSQL + MinIO + Redis
api          -> SMTP + OCR + configured AI providers
```

- `web` 是正式的 Nginx 静态文件服务，生产环境不使用 `vite preview`。
- `api` 默认使用 3 个 Uvicorn worker，只处理 HTTP、SSE 和 Agent 流式响应；其
  `RUN_BACKGROUND_WORKERS=false`，不会在每个 Web worker 内启动耐久任务循环。
- `worker` 运行 `python -m app.worker`，处理耐久操作和场景建模恢复任务。PostgreSQL
  advisory lock 只允许一个有效 worker；即使错误扩容也不会并发消费同一类循环任务，但应仍然
  保持一个逻辑 worker 并监控其租约与日志。MinIO Bucket 初始化也只由这个租约持有者执行，
  API worker 不会在启动时并发创建/探测同一 Bucket。
- `RUNTIME_ENVIRONMENT=prod` 仅决定执行 Action、Workflow、Agent、MCP 时选择已发布
  快照。场景创建、读取、编辑和调试使用 authoring/live 定义，不得再通过把生产环境改为
  `dev` 来规避新场景未发布导致的问题。

## 凭据与环境变量

将 [production.env.example](../deploy/production.env.example) 的键名配置到 Coolify 或受管
Secret Manager。示例文件的 `replace-me` 全部是占位符，不能作为生产值，也不要提交实际的
`.env` 文件。若数据库密码包含 URL 保留字符，应在 `DATABASE_URL` 和
`ALEMBIC_DATABASE_URL` 中按 URL 编码规则处理。

关键分组如下：

| 分组 | 必填项 | 用途 |
| --- | --- | --- |
| PostgreSQL | `POSTGRESQL_*`，可选 `DATABASE_URL`、`ALEMBIC_DATABASE_URL` | API/worker 应使用最小权限运行账号；迁移容器可通过 `POSTGRESQL_ADMIN_*` 或显式迁移 URL 使用 DDL owner。 |
| MinIO | `MINIO_ALIYUN_ENDPOINT`、访问密钥、`MINIO_BUCKETNAME` | 文件、数据集和证据的权威对象存储。生产必须可访问并持久化；`MINIO_REQUEST_TIMEOUT_SECONDS` 约束 SDK 连接和读取超时。 |
| Redis | `REDIS_HOST`、端口和密码（如有） | 可失效缓存；失效不会替代 PostgreSQL/MinIO 的正确性。 |
| SMTP | `MAIL_SERVER`、`MAIL_PORT`、`MAIL_USERNAME`、`MAIL_PASSWORD`、`MAIL_FROM`、TLS 参数 | 注册验证码、邀请和重置密码。`MAIL_STARTTLS` 与 `MAIL_SSL_TLS` 只能启用一个。 |
| OCR | `OCR_BASE_URL`、`OCR_API_KEY` | 图片解析需要；生产 PDF 解析建议配置。API 与 worker 均会获得这两个变量。 |
| 公开 MCP | `AGENT_MCP_PUBLIC_URL`、`AGENT_MCP_ALLOWED_HOSTS` | 仅在需要把 Agent 发布为 MCP 时设置为真实公网地址和精确 Host。 |

`DATABASE_URL` 和 `ALEMBIC_DATABASE_URL` 是可选的显式 URI 覆盖：若留空，API/worker 会从
`POSTGRESQL_*` 安全构建运行连接，迁移容器在 `ALEMBIC_USE_ADMIN=1` 时从
完整的 `POSTGRESQL_ADMIN_*` 构建迁移连接；若管理员凭据留空，会完整回退到
`POSTGRESQL_USER/PASSWORD`，而不会把运行密码错误地配给 `postgres` 用户。这使现有的
`POSTGRESQL_*` Secret 集可以直接用于 Compose；仍应把 API 运行账号与迁移 owner 分开，不能长期用
PostgreSQL 超级用户运行 API。

LLM 的 Base URL、模型和密钥由租户级 LLM 配置管理；生产网络仍需允许 API/worker 访问获准的
AI 服务。`Aide_API_KEY`、`Aide_BASE_URL` 和 `Aide_MODEL` 不是自动导入键，单独写入 `.env`
不会创建或覆盖任何租户模型配置。请通过 LLM 管理 UI/API 为目标工作区保存配置，并在保存后执行
连接测试；这样不会把一个部署级密钥意外共享给其他租户。部署变量不应用来改变平台功能开关或绕过
服务端授权。

`compose.production.yml` 为 API 设置保守的数据库连接池默认值：3 个 API worker 的最大理论
连接数约为 `3 * (DATABASE_POOL_SIZE + DATABASE_MAX_OVERFLOW)`，再加 worker 的连接池上限。
部署前应按 PostgreSQL 的 `max_connections`、其他应用和连接代理容量调整这些值，而不是沿用
开发环境的大池配置。

API 的 Docker 健康检查会验证 PostgreSQL 和 MinIO。默认
`API_HEALTHCHECK_TIMEOUT=60s` 覆盖 `MINIO_REQUEST_TIMEOUT_SECONDS=20` 的一次受限重试；若提高
MinIO 请求超时，也要相应提高健康检查超时。否则健康服务可能在对象存储恢复期间被 Docker/Coolify
误判为失败，进而阻塞 `web` 服务的启动。

## 迁移与发布顺序

先完成 PostgreSQL 备份或快照，再按下面顺序发布。API 启动时只验证 Alembic 版本，绝不会
隐式执行 DDL；因此不能跳过第 2 步。

1. 在 Secret Manager 中准备运行账号和迁移 owner 账号。运行账号不应具备建库、建角色或
   Schema DDL 权限。
2. 用迁移 owner 在新镜像内执行 `alembic -c alembic.ini upgrade head`。当前代码的
   `migrate` Compose 服务就是该一次性任务；Coolify 应将同一命令配置为 pre-deploy job，
   而不是让每一个 API worker 执行迁移。
3. 确认 `alembic current` 与 `alembic heads` 一致，再以运行账号执行
   `python scripts/verify_postgresql_runtime.py`。这一步验证运行时权限和 PostgreSQL/MinIO/
   Redis 的基本往返。
4. 启动 `api` 与 `worker`，检查 `/api/health`、worker 租约日志、注册邮件和一次小文件上传。
5. 启动或切换 `web`，再从公网入口验证 SPA 路由、`/api`、`/mcp` 和 SSE 流式响应。

普通 Docker Compose 可直接使用：

```powershell
docker compose --env-file .\deploy\production.env -f .\compose.production.yml up --build -d
docker compose --env-file .\deploy\production.env -f .\compose.production.yml logs migrate
```

将 `production.env` 存在部署机或 Secret Manager 中，不能放入仓库。首次或升级时应在迁移成功
后才允许流量切到新 API；迁移失败时停止发布并从备份策略恢复，不要以删除 Alembic 版本记录
的方式绕过失败。

生产入口必须由 Coolify 或其他反向代理终结 HTTPS，且保持 `AUTH_COOKIE_SECURE=true`。只有在
隔离的 HTTP 冒烟环境中才可临时设为 `false`；直接把 `http://host:8080` 作为公开生产入口时，
浏览器会拒绝 Secure 登录 Cookie。

## 前端、反向代理与上传

生产构建把 `VITE_API_BASE_URL=/api` 编译进静态前端。Nginx 将 `/api/` 原样反向代理到 API，
并将 `/mcp` 代理到 API 根路径；`proxy_pass` 没有尾部路径，因此不会意外剥离 `/api` 前缀。
上传请求关闭代理请求缓冲，SSE/Agent 响应关闭响应缓冲。外层负载均衡器、WAF 或 CDN 也必须
使用兼容的请求体上限和流式策略。

单个上传文件的应用上限为 **400 MiB（419430400 bytes）**。Nginx 使用 `401m` 仅为 multipart
边界预留 1 MiB，FastAPI 仍以 400 MiB 为精确单文件契约；到达 API 的超限文件返回 JSON `413`，
超过网关包络的请求由 Nginx 直接返回 HTTP `413`。前端应按状态码统一处理两种响应。验证
发布时至少覆盖数据源、Assistant 附件和模板上传的以下情况：接近上限成功、超过上限为 413、
网络中断后临时文件清理、以及流式上传不被反向代理整体缓冲。

本地 Vite 开发服务器使用 `VITE_API_PROXY_TARGET` 指向可达的后端服务地址，例如
`http://127.0.0.1:8001` 或 Docker/局域网 DNS。该变量只作用于开发代理；容器化生产前端不应
访问自身的 `127.0.0.1:8001`，而应经同源 Nginx `/api` 访问 `api:8001`。

## Coolify 与仓库认证

在 Coolify 的代码源中使用 GitHub App **`github-app-renhedata-github`**，并确认该 App 对
`ontology_business` 私有仓库具有读取权限。不要退回到无权访问仓库的 Deploy Key，也不要把
GitHub Token、用户名或密码写进 Git remote URL、Compose 文件、构建参数或日志。若部署失败提示
`Permission denied (publickey)`，先检查 GitHub App 安装范围和 Coolify 的 App 选择，而不是临时
修改仓库地址。

## 多进程发布检查

每次调整 API worker 数量、连接池、Redis 或后台处理逻辑后，在与生产相同的进程数下验证：

1. 并发 HTTP 请求不会耗尽 PostgreSQL 连接池，事务和锁超时符合预期。
2. worker 重启、重复副本和 API 重启不会使耐久任务重复执行；检查 PostgreSQL advisory lock 和
   任务幂等/租约恢复记录。
3. MinIO 大文件上传、文件处理、OCR 和 Agent 调用在 worker/API 进程切换后仍可恢复。
4. Agent SSE 流从 Nginx 到浏览器持续发送，不被 CDN、Nginx 或应用 worker 缓冲或截断。
5. 禁用 Redis 后，核心元数据和文件读取仍由 PostgreSQL、MinIO 正确恢复；Redis 恢复后缓存可重建。

部署配置只决定连接哪套 PostgreSQL、Redis、MinIO、SMTP、OCR 与 AI 服务，不应改变租户隔离、
用户创建、场景编辑或调试能力。数据隔离和资源可见性必须始终由服务端的 tenant、创建者、owner
和授权规则执行。
