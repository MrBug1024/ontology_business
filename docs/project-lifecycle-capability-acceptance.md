## 边界决策

- 项目事实、成员、角色授权、消息、业务审批、计划版本、提醒任务和正式文件由第三方持有。传入最小必要上下文；群昵称仅显示，不是权限身份。
- 能力输出均为建议或待执行请求。第三方确定性校验后提交事实变更、发送消息或交付文件；模型不能声明这些动作已发生。
- 业务评审与平台能力发布治理、执行确认是三种不同机制。新场景不以平台 `approval` 节点实现客户业务审批。
- 离线包不调用本平台、不含凭据、不注册平台 Skill 执行器。离线指不依赖本平台；若第三方选择云模型，仍会按该模型的方式处理上下文。
- 第三方使用在线能力时，调用数据必然到达运行服务。现有工作流会保存加密输入、任务及输出，不能承诺在线模式零落盘或零数据回传。
- 普通场景删除接口实际是可恢复退役。按此机制移除旧场景的活动入口，保留历史审计，不触发永久清除。

## 通用平台现状与旧改动审查

1. `OntologyWorkflowProvider.contract` 将全部工作流定义为需确认的副作用能力；`invoke` 仅返回 `workflow_run_id` 与平台 `task_url`。REST v2、MCP、SDK 的回执接口读取入队回执，没有对应的外部工作流最终结果接口。当前不能声称在线第三方全链路已完成。
2. 工作流编辑器支持 LLM、规则、操作等节点。业务分析可以配置，但输出 JSON 解析不等于严格输出 Schema 校验，专业可靠性不能只靠提示词。
3. 旧轮次的状态长度、嵌套输入序列化、审批恢复重跑模型、确认令牌进入模型均是已复现的跨场景缺陷，保留修复与测试。已应用迁移不改写。
4. 旧轮次 Agent 确认组件和任务产物入口作为可选参考客户端功能保留，不再被新场景定义引用，也不作为第三方完成业务的必经路径。用户原有工作区与账户代码改动保持。
5. 旧方案历史验证见 `docs/ai-product-manager-capability-acceptance.md`。其中平台任务成功不能证明新边界下的交付成功。
