## 2. 应先统一的产品认识

平台交付的是有业务语义、输入输出、治理规则和版本承诺的场景能力。平台内的业务顾问负责辅助建设，验证 Agent 负责体验和验证；它们承担不同职责。

| 概念 | 回答的问题 | 与其他概念的关系 |
| --- | --- | --- |
| 业务需求 | 谁在什么条件下，希望达成什么结果，如何判断成功 | 决定能力边界及验收，驱动模型建设 |
| 业务场景 | 目标、参与者、流程边界与适用情境是什么 | 组织一组有关联的能力，不绑定某个聊天终端 |
| 本体模型 | 对象、关系、属性、状态和约束分别是什么意思 | 让数据、规则、操作和工作流使用一致的业务语言 |
| 数据与实例 | 本次讨论或执行涉及哪些具体事实，来源与版本是什么 | 映射到本体；建模资料、验证样本、正式运行输入分开管理 |
| 场景能力 | 接受什么输入，进行什么判断或操作，返回什么业务结果 | 引用模型、规则、函数、Action、Workflow，形成可调用契约 |
| 发布 | 对外承诺使用哪一套不可变定义和策略 | 冻结能力及依赖；本次数据、连接解析与终端呈现另有归属 |
| Agent 与终端 | 如何理解用户意图、选择能力、组织表达和收集决定 | 消费能力并承载交互，不能替代服务端执行事实 |

建设顺序应从业务结果反推必要语义和能力。不是每个场景都需要对象实例、物理映射、工作流或审批；无数据能力也可以成立。反过来，已经画出本体和工作流，也不意味着业务需求得到满足，仍需实际输入输出和拒绝路径的验收。

数据也不仅是附件：它可能是有来源的业务事实、受管数据版本或当前连接读取。映射负责事实与语义的对应，不能把客户物理表列变成公开能力定义。运行结果只有经过明确、获授权的写入能力才更新业务事实，模型回答本身不构成更新。

## 3. 已核实的现状

### 3.1 Markdown 限制同时存在于前后端

- `frontend/src/views/AgentChat.vue:67` 使用 `PlainMessage` 渲染消息正文。
- `backend/app/services/agent_runtime_adapter.py:1593` 在通用提示词中要求纯文本，禁止 Markdown、表格、按钮和弹窗。
- `backend/app/channel_interaction_schemas.py` 的 `ChannelDeliveryOut.format` 只允许 `text/plain`。
- `frontend/src/components/agent/AgentCapabilityReceipt.vue` 直接显示 `delivery.text`，没有使用 `SafeMarkdown`。

因此，只把正文组件改成 Markdown 渲染，并不能解除模型输出和回执投影中的纯文本限制。当前实现把纯文本渠道的要求施加给了验证中心。

### 3.2 第三方直接调用能力的基础已经存在

`backend/app/routers/external_capabilities.py:412` 接收场景、能力、发布版本和本次输入，直接调用 `capability_application_service.invoke`，不要求先配置或调用平台 Agent。`capability_mcp_service.py` 和 `backend/sdk/ontology_platform_sdk.py` 也有对应能力发现、调用和回执读取入口。

所以这里的优化重点是让产品入口、接入清单、交互契约和验收明确支持这条路径，而非另外新增一套执行内核。能力内部有必要的 LLM 分析步骤也可以成立，这与要求第三方通过平台会话 Agent 转发是两件事。

### 3.3 回到对话的结果链路存在，但完整性仍有边界

`capability_delivery_service.project` 已经把工作流后续状态投影到统一回执；`AgentCapabilityReceipt.vue` 在会话内轮询非终态回执。因此不能把现状描述为“所有结果都只能在运行治理查看”。

但以下路径需要进一步验证：

1. `_result_text` 优先选择结束节点的 `summary`，随后才处理部分结果字段；一般嵌套对象和列表没有完整的业务呈现契约。一个笼统的结束摘要可能遮蔽更有用的中间产物。
2. `_model_receipt_projection` 对超出预算的回执保留标识、结构轮廓和受限摘要，标记 `result_omitted`。这是有界上下文措施；若没有授权的结果分页、明细读取或产物交付闭环，Agent 仍可能无法回答用户真正关心的内容。
3. 回执组件在对话轮次结束后开始读取结果；附件发现也受明确的成功执行证据限制。不能用任意模型链接补齐缺失产物。
4. 当前代码中未发现完整的第三方 webhook 注册、持久投递与重试链路。现有查询能力不能等同于主动交付能力。

这些是静态核查发现的边界与风险，并不能代替对用户具体失败会话的复现。本轮未读取业务数据库和真实会话，不能断言所有“未返回结果”都来自同一原因。

### 3.4 外部审批入口已有，外部人员体系尚未独立表达

`channel_interactions.py`、`channel_interaction_service.py` 和 SDK 已支持读取待办、提交文本决定、证据与 expected revision。现有校验会检查当前 principal、工作区角色、指定平台用户以及审批权限。

这能支持经过认证的外部调用者完成流程，但不等于已经支持任意第三方应用的终端用户身份。不能把某个服务 API key 的身份直接当成所有最终审批人的身份，也不能信任请求体自报的人员姓名。

当前通用回复 DTO 以文本和消息编号为中心。未来第三方 Agent 的首选接口应直接接受有界的决定枚举及证据，文本解析作为终端适配；不要求第三方先组织特定中文句式再由平台解析。

### 3.5 业务顾问的附件链路确实不是正文持续流式

- `assistant.py:7866` 的附件请求先返回受理事件，然后结束初始 SSE。
- `execute_assistant_request_run` 调用非流式 `chat`；普通回答路径使用 `llm_service.chat`。
- `useAssistantRequestRuns.ts:84` 根据 running/queued 等状态写固定文案，轮询结束后重新加载会话。
- 非附件流式路径也会在返回流之前执行上下文和语义路由处理。
- `scenario_model_compiler.py:2116` 等编译路径等待完整 JSON；阶段进度和检查点已经存在，但不等于模型正文流式输出。
- `GlobalAssistant.vue` 已使用 `SafeMarkdown` 并处理 token 事件，因此主要问题是各执行路径的事件供给不一致，而非前端完全没有渲染能力。

### 3.6 建模已有分阶段和校验能力，不能只归因为提示词不够聪明

现有编译器已包含来源覆盖、冲突、依赖、候选、检查点、预算和有界并行逻辑；应在这些基础上调整用例编排。

当前声明了本体、实例、映射、能力、规则、工作流六类阶段。它们可以是可用任务类型，但不能代替针对用户目标的必要性分析。实例和部分逻辑映射还具有草稿语义，必须区分“提出候选”“通过校验”“用户核对”“真实写入”，不能只凭任务标题判断已经创建正式对象。

本轮没有真实模型耗时与质量数据，因此不能给出“换模型即可解决”或具体加速比例的结论。

## 4. 输出格式与能力调用的建议

### 4.1 结构化结果是业务契约，展示格式是交付选择

推荐的调用关系：

```text
业务顾问 -> 辅助建设和验证定义 -> 人工发布

平台验证 Agent -> REST/MCP 对等的应用服务 -> CapabilityInvoker
第三方 Agent   -> REST/MCP/SDK            -> CapabilityInvoker
业务系统       -> REST/SDK                -> CapabilityInvoker

CapabilityInvoker -> 权威业务结果 / 状态 / 证据 / 待办 / 受管产物
                  -> 各调用方组织对话与终端展示
```

每项公开能力提供机器可读的输入输出 Schema、语义说明、适用条件、数据要求、风险、可能等待的交互及错误。内部依赖不应自动全部变成可调用的公开能力，避免绕过组合能力内的强制审批。

建议把回执中的内容区分为结构化业务结果、明确 MIME 类型的展示内容、受管产物和结构化待办。第三方可只消费业务结果，也可采用平台提供的展示内容；接入流程不要求消费平台 Agent 生成的最终回答。

对于普通结果呈现，切换纯文本和 Markdown 不应改变业务结果、定义身份或调用授权。若能力的交付物本身就是 Markdown 文档，其格式属于文档输出契约，应与对话展示偏好区分。

### 4.2 提示词有作用，但不应独自承担格式契约

在平台 Agent 配置中要求“回答使用 Markdown”或“使用纯文本”是合理的表达偏好。建议另外提供明确的格式选项，并由终端声明可接受格式；用户要求与终端能力冲突时明确降级，不静默丢失内容。

- 验证中心默认支持安全 Markdown，沿用 `SafeMarkdown`；用户原始输入保持原文语义。
- 纯文本终端使用纯文本呈现，保留列表、字段关系、链接说明和附件；不能靠简单删符号把表格关系破坏掉。
- 第三方自己的 Agent 由第三方配置提示词，平台只保证所调用能力的契约。
- `channel-delivery/v1` 已是既有公共契约，不能直接改其格式语义。实施时需明确兼容的新增表达或版本演进及一致性测试。

MCP 的工具规范区分 `structuredContent` 和面向呈现的 `content`，也不指定唯一的用户交互界面；这可作为协议适配的依据，不要求升级当前 SDK 才能开始理清平台边界。

## 5. 人工交互与运行治理的建议

### 5.1 保留治理能力，调整其产品职责

平台仍要能查询运行状态、解释失败、核对未知执行结果、追踪审计和处置运维异常。需要保留这些能力，但第三方业务用户不应被要求进入平台页面才能完成业务。

可将“运行治理”的普通定位改为“运行与审计”，作为有权限的平台运营入口。命名本身不能解决问题，核心验收是：关闭这个页面后，第三方依然能完成完整业务流程。

| 情况 | 建议执行方式 |
| --- | --- |
| 普通分析、查询、计算 | 满足输入和权限后直接返回结果，不统一增加人工审批 |
| 可选业务复核 | 由业务定义决定是否需要；第三方可以在自身编排中追加 |
| 已发布的强制业务审批 | 发布契约声明条件、允许决定、角色及证据要求；终端可选择交互形式，服务端校验决定 |
| 高风险或不可逆副作用确认 | 保留 preview -> server confirmation -> execute；确认可来自第三方终端的可信交互 |
| 平台故障、结果未知 | 运维与审计处理，不能显示为业务成功或自动盲重试 |

第三方的自由体现在选择公开能力、组织业务流程、选择交互界面及结果消费方式。已经声明为强制的约束不能由调用时的 `skip_approval` 之类参数绕过。发布不同业务模式可以是显式设计，但不是协议层的旁路。

### 5.2 随能力发布的是可执行的交互要求

建议契约描述触发条件、决定类型、参与者资格、期限、必要证据、拒绝后的行为和恢复点。具体人员或外部组织的身份映射在受治理的部署/接入配置解析；不把本次审批人、群聊或客户连接信息写成通用能力定义。

一次实际待办需要绑定调用、发布与输入版本、待办 revision、发起人与允许参与者。第三方可以使用按钮、表单、任务系统或自然语言收集决定。语义含混时应澄清；“模型说用户同意”不能作为决定证据。

外部人员接入可以先使用现有平台成员映射，后续再引入受信身份提供方及受限授权委托。必须记录调用应用、实际决定主体与授权链。若选择引入不属于现有成员模型的执行主体，需要先明确调整身份契约和根级宪法；不能在实现中偷偷跳过成员校验。

除了确认和审批，还应按业务需求逐步支持补充输入、补充文件、选择分支及任务交接。每种交互都需要可验证的输入契约和状态转换，不宜直接新增一个任意 payload 的万能待办接口。

### 5.3 结果、决定与审计的交付

能力执行始终保留可授权查询的权威结果。短任务可直接返回；长任务返回调用身份后，通过事件流或可选 webhook 通知，再读取结果。第三方可自行选择同步等待、查询、订阅或在自己的终端主动通知用户。

需要区分业务评审结论和平台执行审计。前者是业务结果或业务事件，可以按契约交付；后者是受权限保护的调用证据，不应默认把完整内部日志推给第三方。

webhook 是可选交付方式，不能成为结果是否存在的唯一证明。实施时需要持久 outbox、签名、事件 ID、去重、有限重试、投递状态和重放查询；通知丢失不重新执行业务。回调地址由受治理接入配置引用，并执行现有外部网络边界要求。

## 6. 业务顾问的建议

### 6.1 两类流应同时存在

1. 面向用户的回答增量：可读正文及时流式输出，使用安全 Markdown。
2. 面向任务的事实事件：读取了哪些资料、完成了哪些识别、发现何种冲突、哪些候选通过验证、哪些内容仍待决定。

“一直流式”应解释为整个工作周期持续可观察。有模型正文就流正文，有工具进展就流事件，等待外部处理时显示明确状态；不能用不断重复的句子或伪百分比冒充新进展。

复杂编译结果仍须经过完整结构校验。可以增量展示已形成的候选和来源，但未完成的 JSON 片段、模型内部推理或未经确认的执行状态不作为业务事实。

建议把 HTTP 流式和附件 worker 收敛到同一应用编排与事件出口，保留各自事务和 lease 边界；不要继续分别维护一份 chat 和 stream_chat 的业务分支。持久事件需支持 sequence/cursor、重连去重、最终快照、取消、fencing 和有界保留；前端临时状态不是任务权威。

前端按事件更新正文、资料、任务步骤和产物；用户上翻时停止强制滚动，逐字更新不逐字广播给屏幕阅读器，窄屏与中断状态均可操作。长文按合适频率合并增量渲染，不必每个 token 重排整段历史。

### 6.2 用需求与证据驱动建设

推荐的工作过程：

```text
用户目标与资料
 -> 业务需求、参与者、约束、成功/失败案例
 -> 证据定位、既有模型和能力复用、关键歧义澄清
 -> 必要任务及依赖计划
 -> 本体 / 逻辑映射 / 实例候选 / 规则 / 函数与操作 / 工作流
 -> 确定性校验与局部修正
 -> 输入输出验证、需求覆盖核对、变更预览
 -> 按权限及现有治理正式应用 -> 人工发布
```

不能只有“某段资料生成了哪些实体”的覆盖率，还要能回答“某项业务需求通过哪个能力实现、采用什么输入、何时失败、如何证明”。建议在现有来源覆盖和候选机制上补充这层需求关联，而不是再造第二套治理状态机。

针对各资源的质量判断：

- 本体：对象边界、业务主键、单位、状态、关系基数与时间语义是否一致；避免把报表列直接等同于业务概念。
- 映射：字段含义、类型、单位、枚举、空值和主外键是否匹配；无物理数据时明确保留逻辑映射。
- 实例：值必须有来源，区分验证样本与正式事实；只有核对、授权和持久化完成后才称为已创建。
- 规则：触发条件、冲突、优先级与例外可解释；可以是建议或约束，但必须明确语义。
- 操作：有真实受支持的执行绑定、输入输出和风险契约；有名称与描述不代表已经可执行。
- 工作流：节点数据能传递，分支条件完备，等待、拒绝、失败和重试行为可验证；不能仅检查连线存在。

澄清应集中在确实影响执行正确性的歧义。已经确定且相互独立的草稿工作可以继续，阶段内部进度不必每一步都让用户确认；发布和适用的正式写入门禁仍保留。

### 6.3 精准性与效率分别测量

先记录解析、检索、路由、编译、校验、修正与模型调用的耗时和预算，再确定瓶颈。现有有界分块并行与检查点应优先复用。

建议优化点包括复用已解析资料、仅检索相关证据、按依赖并行独立任务、携带结构化校验错误进行局部修正，以及对用户修改做依赖失效分析。缓存必须绑定 tenant、访问权限、资料版本、编译器与模型配置版本，不能用缓存绕过最新授权。

评测至少分别记录需求覆盖、语义正确性、合法引用比例、一次校验通过率、修正次数、首次真实进展时间、总耗时和调用成本。按场景规模分类建立基线后再确定目标；不能用多输出几条进度消息代替效率提升。

## 7. 建议实施顺序与验收

| 顺序 | 交付范围 | 关键验收 |
| --- | --- | --- |
| 1 | 确定结果、格式与交互边界；恢复验证中心 Markdown 和结果呈现闭环 | 同一已发布能力在验证中心与纯文本参考终端返回同一业务结果；长结果、嵌套结果、附件和失败均可取得；用户不用访问运行治理 |
| 2 | 贯通业务顾问全路径真实事件与正文流 | 附件/非附件、工具/编译、刷新/重连、取消/重试均有一致事件语义；首段在模型结束前出现，结束后不丢失最后一页事件 |
| 3 | 完善第三方原生交互与异步交付 | 不创建平台 Agent 的独立客户端完成发现、调用、确认、审批、补件和结果获取；可信身份、过期决定、重复投递和版本冲突通过真实 PG 验证 |
| 4 | 优化需求驱动的建设编排与增量修正 | 在固定案例集上证明语义质量和效率变化；完整搭建后能按明确输入调用能力；修改局部需求不无谓重建全场景 |

第 3 步中的新补件、身份委托和 webhook 是新增能力，应分别明确范围；不能把已有文本审批接口的通过结果当成这些功能的验收。

建议贯穿四步使用同一组场景：零数据分析、结构化计算、文档分析、多来源冲突、需要可信人工决定的操作、异步生成产物。至少一个完整场景由第三方参考 Agent 直接消费，证明平台 Agent 和平台管理页面均不是必经入口。

正式验收应覆盖：不同输入数据不改变定义、旧发布不受编辑影响、输出格式不改变业务结论、缺权限拒绝、迟到响应不覆盖新任务、未知结果不盲重试、实际执行成功与单纯受理明确区分。
