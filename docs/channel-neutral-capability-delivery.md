## 已核实的原因

1. `OntologyWorkflowProvider.contract` 将所有工作流声明为副作用且要求确认；包括仅有 start/llm/end 的分析流程。`invoke` 只允许 confirm 模式。
2. 入队返回的是 `workflow_run_id/status/task_url`。公共 `get_receipt` 读取原 CapabilityInvocation 入队回执，并没有映射后续工作流最终结果；“能力调用成功”不足以代表业务处理成功。
3. 新增的 `AgentCapabilityReceipt.vue` 依赖确认按钮、弹窗及跳转任务页面，没有在对话中接回异步结果。关联任务已记录这一在线通用缺口，但只在场景配置和离线参考包中绕开。
4. 模型 `chat_stream` 已逐段返回文本；`CapabilityAgentRuntime.run_agent` 却先缓存整个模型轮次再 yield token。持久 Turn 的 `invoke_agent_once` 再次收集全文，只在结束后交给 worker。前端 SSE 因此只有阶段状态与终态全文。
5. `CapabilityAccess.vue` 默认 dev，显示的是定义解析/Manifest，而非人工发布列表；页面没有人工创建发布的主入口。现有 publish_snapshot 是显式命令，尚未发现“平台自动决定创建发布”的证据。这里应区分 UI 含义误导、readiness 拒绝和实际发布动作。

## 产品与契约方向

### 渠道交付

- 标准交付同时包含可直接发送的纯文本和结构化结果；Markdown、按钮、弹窗是渠道可选表现。文件是受权访问的附件资源，真实 @ 由连接器根据稳定人员 ID 投递，昵称仅显示。
- 区分普通分析、受治理副作用授权、业务评审三个语义。分析直接执行；副作用仍遵循预演与服务端确认；业务决定由有权人员在自己的终端提交，运行治理仅用于审计/排障。
- 待办至少绑定请求标识、外部会话/事项上下文、内容版本、允许决定、指定人员或角色、必需证据、有效期和修订号。可信连接器携带操作者稳定身份；通用模型不能自称某人批准。歧义回复先澄清；明确回复也必须过权限与版本校验。
- 执行结果未知保持 indeterminate，重复消息复用持久幂等；接收消息、业务批准、实际执行成功分别记录。附件上传不代表证据已被认定有效。
- 第三方持有其项目/业务权威数据；平台在线执行只消费本次显式最小输入，公开说明实际保存的运行记录。在线处理不等于零数据回传或零落盘。

### 真实流式

- 模型正文直接进入有界增量缓冲，首段及时提交，后续按短时间窗合并；公开事件仅含正文和安全阶段状态，不复制工具参数及密钥。
- 既有持久 Run/Event 承载当前正文快照与增量事件。短事务重新核验执行主体及 lease/fence，避免请求 session 持有长事务或用进程字典做权威。
- 客户端按 revision 去重、按正文 offset 接续；GET 当前快照与 SSE 补发一致。新一轮模型回答显式重置草稿正文，最终答案由终态覆盖。
- SSE 终态只在当前事件分页被完整消费后结束，防止长回答重连时超过单页上限而截断。

### 人工发布（用户已批准宪法调整）

- 主入口为发布列表：场景、发布名称/版本、创建人/时间、启用状态、操作。创建表单选择场景并展示能力摘要，确认后冻结当前场景能力及依赖。
- 正式版本不因 UI 环境选项改变语义。启用、停用、退役、删除均由人工明确操作；删除仅移出活动管理列表，保留被历史调用引用的不可变定义与审计。
- 创建时默认停用，创建成功后由人工启用。同一场景同时只允许一个启用版本；切换时人工停用原版本再启用新版本，数据库唯一约束与场景锁共同保证并发正确。
- 服务端验证主体、权限、契约合法性和依赖闭包。质量建议作为可见报告；不自动发布，也不以评分替人工做业务发布决策。
- 旧 dev/staging/prod 是已经发布的协议字段与持久状态，不能只隐藏 UI 或静默换义。需明确迁移、兼容读取/弃用窗口、旧发布冲突处理，并通过真实 PG 和协议一致性测试。
