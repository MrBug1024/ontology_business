# 需求与文档

## 痛点挖掘

按用户群体分别记录：角色、真实任务、触发条件、当前做法、问题发生频率、可观察影响、现有替代办法、约束与证据。不要把不同客户的相反诉求合并成一致需求，也不要把“要 AI 日报”直接认定为需要日报功能。

需要验证的假设说明：哪一条证据支持、仍缺什么、向谁确认、什么结果会推翻假设。问题优先选择能改变方案、范围或价值判断的内容；已给出的事实不要重复询问。原话明确排除的诉求保持排除，不再当作潜在功能重新询问；没有提供某文档不等于文档不存在或尚未编写。

## 需求条目

每项具有 ID、用户任务/目标、证据引用、范围、业务规则、成功与异常路径、数据/权限、可观察验收、依赖、待确认项。建议新增的字段、流程或限制必须明确是建议，不能混入已确认范围。

验收采用“前置条件 -> 操作 -> 可观察结果”，分别覆盖认证、授权、必填/格式、幂等、并发与错误路径中实际适用的部分。不要把缺字段等同于未登录，不把确认前取消扩展为事后撤销，不为通用模板强造额外流程。

输入没有明确提供的状态机、按钮、接口、异常文案、数据保存和取消窗口不能写成现状或正式需求。原话中的时间边界必须保留；例如不能从“提交前可取消”推导出“确认提交后尚有待受理窗口”。新验收建议明确以“建议”开头，未决定行为以“待确认”开头。不要声称文档已有颜色标注、图示或附件，除非实际生成并检查过这些内容。

优先级结合用户价值、业务价值、风险、紧迫性、依赖与成本解释取舍。只有项目明确提供评分尺度/权重及全部输入时才能计算，不默认 0-100 或高/中/低阈值。没有估算时请研发给出估算，不能“暂定两周”。

## Word PRD

`document` 中每个 section 是一章，paragraphs 是封闭段落对象数组，evidence_ids 指向本次上下文的证据。`kind=evidence` 时只引用 ID，text 必须为 null；工具按可信 context 填入原文，不接受模型生成的事实段落。新增内容只能是 suggestion 或 question，由工具标明建议/待确认。通常需覆盖：背景与目标、用户与痛点、范围与排除、流程与功能、数据与权限、异常与非功能要求、验收标准、依赖与风险、计划待定项、决策与变更记录。章节可按项目裁剪；不适用说明依据。

使用 `render_prd.py` 在第三方本地生成可编辑文档。交付前重新打开检查标题层级、表格、中文显示和分页，内容与审阅版本一致。修改内容后由第三方重新计算 SHA-256 并重新发起对应评审。文件名不是内容身份。

文档质量检查必须包括：证据可追溯、事实没有新增、未决没有被默认为同意、需求与验收对应、职责可执行、范围一致、版本明确。格式美观不代表内容准确。
