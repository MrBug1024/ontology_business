# 生命周期协作指南

先确定项目当前已确认的阶段、业务目标、商业约束和本次问题。一个项目可以研发与商务并行，已有项目也可以直接处于维护阶段。没有证据时标阶段待确认。

| 环节 | 需要核对的证据/输入 | 优先协作角色 | 专业产出与门槛 |
| --- | --- | --- | --- |
| 商机与商务交接 | 客户目标、联系人授权、合同或订单状态、约定范围与排除项、交付/验收/付款条款、前提依赖 | 项目提供的商务或市场负责人；涉及条款请其协调法务/财务 | 交接缺口清单。缺合同不自动断定一切工作禁止；请求有权限人员确认允许开展的范围及风险承担 |
| 启动与责任确认 | 项目目标、成功指标、关键联系人、决策权限、研发经理、现有计划、升级路线 | 项目负责人、产品负责人、研发经理 | 角色与职责草案；研发经理确认开发人员、职责、可用性，不能由模型分配未经确认的人员 |
| 痛点与需求发现 | 用户原话/行为、任务频率、当前替代方案、影响、限制、不同群体差异 | 产品、客户业务代表、市场/商务 | 分开需求表达与实际问题，给待验证假设、访谈问题及证据到需求的追溯 |
| 需求评审 | 范围、流程、权限、异常、验收标准、冲突、待决策事项、PRD 版本 | 产品负责人；可行性由研发经理会审；客户范围由授权代表确认 | 外部评审请求，明确批准的内容和排除项；变更后旧批准不能套用到新内容 |
| 技术方案与计划 | 需求基线、接口/数据约束、技术不确定性、估算、依赖、成员能力/可用性 | 研发经理和对应技术负责人 | 请求方案、验证方式、分工、工作量与计划；AI 只做完整性和一致性检查，不伪造估算或分配承诺 |
| 实施与验证 | 当前基线、实际结果、阻塞、证据新鲜度、测试和缺陷、变更申请 | 执行责任人、研发经理、产品负责人 | 状态与差异、风险与待协调请求。自报 80% 不代表测试通过或可交付 |
| 交付与验收 | 约定交付清单、验收标准/记录、已知问题、部署/培训/移交方案、客户授权验收人 | 交付负责人、产品、研发、客户授权验收人 | 对照合同/基线逐项检查，形成外部验收请求。发送文件不等于客户验收，部分验收不能写整体完成 |
| 持续跟进与收款准备 | 客户反馈、保修/服务约定、验收事实、付款条件、开票信息及财务流程 | 客户成功/售后、商务、财务 | 跟进计划建议、剩余义务、收款材料清单；由财务确认是否到期、开票与到账，不从交付事实推断已收款 |

每次只提出与当前问题相关的协作请求。不要把全生命周期清单逐项塞进群聊。问题应能由接收者直接回答，说明对应事项、需要补充的材料/决定、依据和已约定期限；没有期限就留空并请求负责人确认。只有本次输入明确给出硬前提时才建立请求依赖，不能擅自让可并行的信息收集等待；研发人员和可用性确认可以与商务材料、需求澄清并行，完整估算的前提不等于一切研发沟通的前提。

发生拒绝或要求修改时，返回具体异议、受影响内容、需要谁补充，以及待重新提交的范围。超时不是默许，沉默不是批准。升级对象及等待周期由第三方项目策略提供，不硬编码“次日”或“48 小时”。
